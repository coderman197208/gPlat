**属实。** 这确实是个逻辑缺陷，不过实际中几乎触发不到。

**代码路径与描述一致**
- `ngx_c_socket_request.cxx:138-151`：遇到 EAGAIN/EINTR 时只打一条日志就 `return -1`，没有调用 `ngx_close_and_recycle()`。可是对端关闭（`ngx_c_socket_request.cxx:128-133`）和其它错误（`ngx_c_socket_request.cxx:170-171`）也都返回 -1，调用方分不清是哪种情况。
- `ngx_c_socket_request.cxx:32-50`：只要 `reco <= 0`，就按断开处理，依次执行 `CancelRequest`、`CancelSubscribe`（会连同 `ClearTagList`）、`ClearPostList`，并停掉超时定时器。
- 但这时 fd 还在 epoll 里，收包状态机也没动。readb/writeb 等请求照常能用，只有订阅相关的状态被悄悄清掉了。

**一旦触发，后果比"取消订阅"更严重**
- 客户端不知道自己的订阅没了，之后再也收不到 POST。
- 正在执行 `waitpostdata(timeout)` 的客户端：`m_bWaitingPost` 仍为 true，但订阅已删、定时器已停，服务端既不会推送数据，也不会回 WAIT_TIMEOUT。
- 正在执行 `getresponse` 的客户端：请求被摘掉，定时器也被取消（`ngx_c_slogic.cxx:1511-1514`），永远等不到回复。
- 这两个接口在客户端都用阻塞的 `readn`，没有本地超时（`higplat.cpp:1583`），所以会一直卡住。

**为什么实际中几乎触发不到**
- **EINTR**：连接 fd 由 `accept4(..., SOCK_NONBLOCK)` 创建，是非阻塞的（`ngx_c_socket_accept.cxx:42`）。Linux 的非阻塞 TCP `recv` 在检查信号之前就会返回 EAGAIN，所以基本不会出现 EINTR。
- **EAGAIN**：epoll 用的是 LT 模式，只有 epoll 线程在读，而且只在 `revents & EPOLLIN` 时才调用读处理函数（`ngx_c_socket.cxx:749`），正常情况下不会读到空。万一真的发生，日志里会出现"errno == EAGAIN || errno == EWOULDBLOCK成立，出乎我意料！"。

**修复思路**：EAGAIN/EINTR 时改为 `return 0`。对端关闭已经对应 -1，所以不会混淆。调用方只在 `reco < 0` 时做清理，`reco == 0` 时直接返回。需要的话我可以直接改。
