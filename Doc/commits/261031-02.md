gplat负责提供订阅服务和数据读写功能，其核心地位和重要性不容质疑，为了给众多客户端提供实时服务，需要频繁地建立和断开连接，频繁地分配和回收内存，涉及读写数据的各种锁机制，以及定时器等复杂异步响应机制。程序中任何细微的漏洞和bug都有可能造成gplat进程的崩溃，对于能源系统的运行场景，这样的代价是完全不可接收的。虽然项目中有测试套件用于测试，但鉴于应用场景的复杂性，测试程序显然不能覆盖所有可能出现的情况，因此需要你这样优秀的、经验丰富的最最顶尖的专家对软件进行最严格苛刻的审阅。包括但不限于：重点核查测试较难覆盖的线程交错：取消定时器时回调是否仍在执行、断连清理是否会与在途请求交叉，以及退出时资源释放顺序是否安全。

# 20261031-02 gplat 并发审阅（二）：断连清理 × 在途请求、定时器取消 × 回调执行、退出释放顺序

## 一、断连清理 × 在途请求

### 根因（R1/R2/R3 共同）

`threadRecvProcFunc` 在线程池入口检查 `pConn->iCurrsequence != pMsgHeader->iCurrsequence`，但**不持锁**。检查通过之后、处理函数拿到连接锁之前，epoll 线程可以完成整个断连流程：

```
epoll 线程                                    线程池线程
                                              threadRecvProcFunc: 序号相等，放行
ngx_close_and_recycle: close(fd), ++序号
ngx_cleanup_closed_connection:
  CancelRequest
  lock(logicPorcMutex)
  CancelSubscribe / ClearPostList
  m_bWaitingPost = false / 停超时定时器
  unlock
                                              HandleXxx: lock(logicPorcMutex)
                                              —— 照常修改连接状态（订阅、等待、注册）——
```

后果是在一个**已关闭**的连接上重新建立了状态，而清理已经做完、不会再来第二次。连接锁内拿到的序号是可靠的：`++序号` 发生在清理获取 `logicPorcMutex` 之前，所以凡是晚于清理拿到这把锁的处理函数必然看到新序号。

### R1：WAIT_TIMEOUT 发到被新连接复用的 fd（高）

晚到的 `HandlePostWait` 把 `m_bWaitingPost/m_bWaitingTimeout` 重新置真并启动超时定时器。定时器回调构造包时取的是**回调执行时的当前序号**（已含断开的那次自增），于是 `msgSend` 的序号检查形同虚设，`send()` 落在旧 fd 号上。Linux 把最小的空闲 fd 号分给下一个 accept 的连接，因此**下一个新连上的客户端会在流里收到一个不请自来的 POSTWAIT 包**（它若正在等别的应答，就会判定协议错误而断线）。

复现（`race.postwait_close_no_crosstalk`）：8 个连接各流水线发 200 个 `POSTWAIT(250ms)` 后半关闭，随即新连 8 个连接（什么都不发）。旧代码 8 轮里 7 轮有新连接收到数据。

### R2：遗留订阅 / PLC 注册（高）

晚到的 `HandleSubscribe` 把已断开连接挂进 `CSubscribe`，`HandleRegisterPlcServer` 把它登记为该 tag 的 PLC I/O 服务器。连接对象经 `Sock_RecyConnectionWaitTime` 回收后被新客户端复用，新客户端就会收到它从未订阅的事件；PLC 注册的情况更糟：写 PLC 的指令会投给一个无关客户端（或丢失），且晚到的注册可能**顶替**已重连的 s7ioserver 的注册。

复现（`race.subscribe_close_no_stale`）：连接池 4 个、回收 1 秒；24 个连接各流水线发 300 个 SUBSCRIBE/REGISTERPLCSERVER 后半关闭；回收后开 32 个只连不订的探针连接，再写 tag。旧代码有 4 个探针收到事件。

### R3：GETRESPONSE 晚于 CancelRequest（中）

晚到的请求照常入队，以已断开的请求方占住 request_tag：若无响应方则一直占到它自己的超时（客户端给的超时没有上限）。

### 修复

1. **连接锁内复核序号**（`ngx_c_slogic.cxx`）：`HandleSubscribe`、`HandleRegisterPlcServer`、`HandlePostWait` 取得 `logicPorcMutex` 后若序号已变，直接返回；`HandleGetResponse` 在 `m_reqMutex` 内复核（`CancelRequest` 也在序号自增之后持这把锁）。
2. **投递路径纵深防御**：不再依赖“不会有遗留记录”。
   - `EventNode` 增加 `seq`（订阅时的连接序号），PLC 注册表改存 `PlcIoServer{连接, seq}`（`CSubscribe.h`）；`Attach` 去重按连接实例。
   - `BuildPostPacket` 改为用订阅/注册时的序号，而不是投递时的当前序号。
   - `DeliverPostLocked` 先比对序号：不符即丢弃并返回 `false`，绝不进入新实例的待发队列、不碰它的等待状态；调用方（`NotifySubscriber` / `NotifyTimerSubscriber` / `NotifyPlcIoSever`）随即 `DetachStale*` 清掉这条遗留记录。PLC 注册失效时按“没有 PLC 服务器”记错误日志。
   - 发送路径的 `msgSend` 本就在 `sendMutex` 下比对包内序号，现在包内序号可信，连接一断即丢。
3. `GetOneToUse` 改为按 `logicPorcMutex → sendMutex` 加锁并 `ClearPostList()`：对象躺在空闲表期间若有迟到的入队，不带给新客户端。
4. `iCurrsequence` 改为 `std::atomic<uint64_t>`：它在多处不持锁读取（线程池入口、epoll 循环），原来是形式上的数据竞争。

## 二、定时器取消 × 回调执行

### 背景：cancel() 不等待正在执行的回调

`TimerManager::processExpiredTimers` 弹出到期节点后**解锁再执行回调**。此时另一个线程 `cancel(id)` 仍返回 `true`，但回调已经在跑。`cancel()` 也**不能**等待它：调用方（`DeliverPostLocked`、断连清理）持有 `logicPorcMutex`，而回调要获取的正是这把锁，等待即死锁。所以正确做法是让回调**持锁后自己核对**它要处理的对象是否仍然有效。逐个核查现有定时器：

| 定时器 | 取消后回调仍执行时 | 结论 |
|---|---|---|
| getresponse 超时 | `weak_ptr` + `DetachRequestLocked` 按指针身份查找，已结束的请求查不到 | 正确 |
| POST_DELAY 延时投递 | 回调内比对包内序号 | 正确（但见 T3、E1） |
| 5 个周期定时器 | 从不取消 | — |
| **waitpostdata 超时** | 只看 `m_bWaitingTimeout` | **错误（T1）** |

### T1：等待超时定时器身份不可验证（中）

回调只检查 `m_bWaitingTimeout`，分不清它属于哪一次等待：

- 投递到达时 `DeliverPostLocked` 取消定时器，但回调已在等连接锁；客户端随即发起下一次等待（`m_bWaitingTimeout` 又为真），旧回调拿到锁后把**新的等待**提前结束。
- `StartTimeoutTimer` 直接覆盖 `m_timerID`，不取消旧的（裸协议连发 POSTWAIT 即可触发），旧定时器成为孤儿，到期时结束之后的某次等待；连接断开后它还会作用到复用该对象的新客户端。
- 回调构造包用的是当前序号（见 R1）。

复现（`race.postwait_superseded_timer`）：`POSTWAIT(1500)`，50ms 后 `POSTWAIT(100)`，收到超时后再 `POSTWAIT(3000)`。旧代码这次 3000ms 的等待在 1350ms 时被 1500ms 的孤儿定时器结束。

修复（`ngx_c_socket.cxx` / `ngx_c_socket.h` / `ngx_c_slogic.cxx`）：
- 连接增加等待代次 `m_waitGen`。`StartTimeoutTimer` 先取消上一次的定时器，再以 `{序号, ++代次}` 作为本次等待的身份捕获进回调；回调持锁后要求 `m_bWaitingTimeout && 代次相同 && 序号相同` 才发超时包，并用捕获的序号构包。
- `StopTimeoutTimer` 取消后把 `m_timerID` 置 -1，没有定时器时安静返回（原来打印 “m_timerID < 0!”）。
- `HandlePostWait` 开始新的等待前先停掉尚未结束的上一次；断连清理无条件 `StopTimeoutTimer()`。

### T2：已取消节点滞留堆中（中，资源）

`cancel()` 只把节点标记无效、从 `timers_` 删除，节点连同回调对象留在堆里直到**原定到期时间**。waitpostdata 带长超时且投递频繁、getresponse 带长超时时，每次等待/请求都留下一个节点：内存 ∝ 频率 × 超时（例如每秒 1000 次投递、60 秒超时，单个客户端就是 6 万个节点；超时上限是 INT_MAX 毫秒 ≈ 24.8 天）。

修复（`include/timer_manager.h`，接口不变）：
- 堆改为 `std::vector` + `std::push_heap/pop_heap`，节点记录 `in_heap`，计数堆中已取消的节点；取消的是堆顶时弹掉堆顶的已取消节点再重置 timerfd；已取消节点超过一半（且 ≥1024）时整体清理一次，均摊 O(1)。
- `processTimers` 计算 epoll 超时时先比较再截断到 `INT_MAX`，避免无符号相减后窄化成负数变成 1ms 忙等。
- 构造函数检查 `eventfd` 失败；析构关闭 `wakeup_fd_`；类注释写明 `cancel()` 的语义。
- 定时器线程不再向控制台打印（`"......No events..."`、周期定时器的 `std::cout`、超时回调的 `"超时时间到"`）：stdout 若是没人读的管道/被暂停的终端，唯一的定时器线程会阻塞在 write 上，所有超时、延时投递、定时器订阅随之停摆。

### T3：EnqueuePost 释放后读（中，ASan 发现）

延时投递回调以 `PkgHeadOf(p_postbuf)->itemname`（指向事件包内部）作为事件名调用 `DeliverPostLocked`。队列已满时 `EnqueuePost` **先释放**事件包，**再**用这个名字写限频日志，读的是已释放内存。新写的停机用例在 ASan 下首先撞到的就是它：

```
READ of size 1 ... thread T4 (定时器线程)
  ngx_vslprintf ← ngx_log_stderr ← ngx_connection_s::EnqueuePost ← DeliverPostLocked ← POST_DELAY 回调
freed by thread T4: CMemory::FreeMemory ← ngx_connection_s::EnqueuePost
```

修复：先记日志再释放（`ngx_c_socket_conn.cxx`）。这不是只在停机时才有的问题，只要延时订阅者不取事件、队列满，就会触发。

---

### T4：定时器 ID 溢出（中）

`next_id_` 是 `int`，每次 waitpostdata（带超时）、getresponse、延时投递都分配一个。按每秒 1 万次计算，约 2.5 天就超过 `INT_MAX`：有符号溢出是未定义行为，实际回绕成负数后，调用方 `if (id >= 0) cancel(id)` 的判断让这些定时器再也取消不掉（只能等到期）；再回绕一圈后，长寿命定时器的 ID 可能与新定时器重复，`timers_[id]` 被覆盖、`cancel` 取消到别人的定时器（例如某个连接的等待永远不超时）。能源系统按月运行，这是现实的长期运行缺陷。

修复：`TimerManager::TimerId = int64_t`，`m_timerID`、`PendingRequest::timerId` 随之改为该类型。

### T5：同一毫秒到期的定时器顺序（低）

堆只按 `expire` 比较，堆不是稳定排序。同一 tag 在同一毫秒内被写两次，两个延时投递的到期时间相同，触发顺序不确定。修复：到期时间相同时按 ID（创建顺序）比较。

## 三、退出时资源释放顺序

### E1：先释放连接池、后停定时器线程（高）

旧顺序（`ngx_worker_process_cycle`）：

```
g_threadpool.StopAll();
g_socket.Shutdown_subproc();   // 等发送/回收线程退出 → clearconnection() 析构并释放全部连接对象，销毁发送队列互斥量/信号量
g_tm.stop();                   // 此前定时器线程一直在跑
```

`Shutdown_subproc()` 要等回收线程（每 200ms 醒一次）退出，期间及之后到期的回调（延时投递、等待超时、定时器订阅、getresponse 超时）都会锁连接对象里的互斥量、调用 `msgSend`。复现（`race.shutdown_with_busy_timers`）：4 个连接做不同延时的 POST_DELAY 订阅并订阅 `timer_500ms`，另一连接高频写 tag，写的过程中 SIGTERM。在旧代码上只补上 T3 的修复以排除干扰，ASan 4 次中 2 次报：

```
heap-use-after-free ... thread T4（定时器线程）
  NotifySubscriber::<POST_DELAY lambda> ← TimerManager::processExpiredTimers
freed by thread T0 here:
  CMemory::FreeMemory ← CSocekt::clearconnection ← CSocekt::Shutdown_subproc ← ngx_worker_process_cycle
```

修复：`g_tm.stop()` → `g_threadpool.StopAll()` → `g_socket.Shutdown_subproc()`。定时器线程最先停，之后线程池里在途请求新加的定时器不会再触发（停机时未到期的延时投递缓冲区随进程退出释放，属于已知的 shutdown-leak 范畴）。

### E2：线程池停机唤醒丢失（中）

`StopAll()` 不持 `m_pthreadMutex` 就置 `m_shutdown = true` 再 `broadcast`。某个线程刚在锁内判断完 `m_shutdown == false`、还没进入 `pthread_cond_wait()` 时，广播落空，它就永远等下去，`pthread_join()` 卡死，worker 无法退出（systemd 只能等超时后 SIGKILL）。修复：在互斥量内修改 `m_shutdown`。

### E3：worker 信号处理函数自死锁（中）

`ngx_worker_process_init` 原来把信号屏蔽字清空，所有线程都会接收 SIGINT/SIGTERM/SIGHUP/SIGQUIT/SIGIO/SIGCHLD。处理函数 `ngx_signal_handler` 写日志要取 `ngx_log.log_mutex`（非递归）。信号若落在**正在写日志**（持有该锁）的线程上，这个线程就自死锁，随后所有写日志的线程都卡死，服务挂住而进程不退出（master 收不到 SIGCHLD，外部看不出异常）。前台运行时 Ctrl+C、systemd 默认 `KillMode=control-group` 都会把信号同时发给 worker。另外 SIGUSR1/SIGUSR2/SIGALRM 的默认动作是终止进程，误发给 worker 会让整个服务下线。

修复（`ngx_process_cycle.cxx`、`ngx_signal.cxx`）：
- 抽出 `ngx_fill_blocked_signals()`（master 原有的那组信号），worker 用它**保持屏蔽**；worker 的退出本来就只经 socketpair 通知，处理函数对 worker 也什么都不做，行为不变。
- `SIGPIPE` 全进程忽略（与 nginx 相同）：守护进程模式下 stderr 仍是启动时的终端/管道，管道读端退出后写日志会被 SIGPIPE 杀死。
- 信号处理函数返回前恢复 `errno`（TSan 报 “signal handler spoils errno”，master 的 SIGCHLD 里 `waitpid` 会改它）。

### E4：重复的 SIGINT/SIGTERM（低）

master 收到第一个信号就 `close(sockpair[1])`，第二个信号又对这个旧 fd 号 `write` + `close`；期间 master 日志轮转可能复用了这个号，于是往日志里写一个 `x` 并把日志 fd 关掉。修复：`ngx_notify_workers_exit()` 只做一次，关闭后置 -1。

## 四、事件顺序：先应答、后投递（O1，高，既有缺陷）

验证阶段 ASan 全量运行中 `pubsub.pending_queue_capped` 偶发失败：订阅者收到的事件顺序是 …2, 4, 5, 6, 3…。追查发现这是**既有缺陷**，与本轮改动无关。

`HandleWriteB`/`HandleWriteQ`/`HandleWriteBString`/`HandleWriteBPlc` 都是先 `SendHeadReply` 应答发布者，再 `NotifySubscriber` / `NotifyPlcIoSever` 投递。发布者（`libhigplat` 的写调用要等应答）收到应答就会发下一次写，这次写可能由另一个消息线程处理；只要前一个线程在“应答之后、投递之前”被抢占（或订阅者多、投递要逐个经过它们），后一次写的事件就先进入订阅者的队列。订阅者最终看到的是旧值；对 s7ioserver 而言，同一个客户端先写 50、再写 60 的设定值，可能以 60、50 的顺序写进 PLC，**PLC 最终停在 50**。

复现（`race.post_order_single_publisher`，4 个消息线程）：先让 100 个订阅者订阅 tag（模拟一个 tag 多个订阅者），再由一个发布者顺序 `writeb` + `write_plc_int` 3000 次，检查订阅者和已注册的 PLC 服务器收到的序号是否单调递增。为放大窗口，把 worker 的所有线程钉到同一个 CPU 并在该 CPU 上加一个忙等线程。未修改的 HEAD 上 3/3 失败（订阅者乱序 8/6/2 次，PLC 乱序 4/7/0 次）。

修复：四个写处理都改为**先投递、后应答**。发布者收到第 i 次的应答时，第 i 次的事件已经进入每个订阅者的发送路径或待发队列，第 i+1 次的事件只能排在它后面（发送路径对同一连接本就保序，延时投递见 T5）。修复后 5/5 通过、零乱序。代价是发布者的写调用要等投递做完才返回，订阅者很多时写延迟会相应增加（每个订阅者是一次分配 + 加锁入队/非阻塞发送，通常为微秒级）。

仍未保证的：**不同发布者**并发写同一 tag 时，Board 的最终值与订阅者最后收到的事件可能不一致（写 Board 与投递不是原子的）。需要按 tag 串行化“写 + 投递”，属于设计调整，见第六节。

## 五、其它加固（低）

- **H1 epoll data 联合体误读**：退出通知的 fd 以 `data.fd` 注册，连接事件以 `data.ptr` 注册，判断时却对所有事件比较 `data.fd == sockpair[0]`，等于拿连接指针的低 32 位和 fd 号比较，理论上会把某个连接事件误判成退出通知。改为以 `data.ptr = nullptr` 作标记。
- **H2 回收宽限期用单调时钟**：`inRecyTime` 与比较用的当前时间改为 `CLOCK_MONOTONIC`。原来用 `time(NULL)`：校时向后跳会长时间不回收（连接池持续扩张、永不收缩），向前跳会让宽限期失效。能源现场普遍有 NTP/GPS 校时。
- **H3 TSan 报出的数据竞争**：`g_stopEventChild`（主线程置位，发送/回收线程轮询）改为 `std::atomic<int>`；线程池 `ThreadItem::ifrunning`（`Create()` 轮询）改为 `std::atomic<bool>`。修复后并发用例在 TSan 下零报告，以后的 TSan 运行不会被这些噪声淹没。

## 六、未修改 / 需要设计决策的风险

1. **getresponse 迟到响应会被错配（建议优先处理）**：响应只按 response_tag 匹配，没有请求标识。当前请求超时或请求方断开后，下一个请求立即开始；响应方随后为**上一个请求**写的响应会被 `DeliverResponse` 交给**下一个请求方**。对能源控制类命令，这意味着可能把 A 命令的执行结果当成 B 命令的结果返回。要彻底解决需要改协议（服务端给每个请求盖序号、响应方回带），或采用“放弃的请求需等其迟到响应或宽限期结束后才启动下一个”的策略，属于语义变更，本轮未动。
2. **worker 崩溃即全站下线**：master 收到 SIGCHLD 就退出，不重启 worker。建议由 systemd `Restart=always` 兜底，或在 master 中重启 worker（Board 锁在 `LoadQ` 时重新构造，重启是安全的）。
3. **accept 遇 EMFILE/ENFILE 时忙等**：水平触发下监听 socket 持续可读，epoll 线程空转并每轮写一条 CRIT 日志（可能写满磁盘）。建议暂时摘除监听事件或预留一个 fd。
4. **超时/延时没有服务端上限**：waitpostdata、getresponse 的超时和 POST_DELAY 的延时都可到 INT_MAX 毫秒。T2 解决了“已取消节点”的堆积，但在途的延时投递仍按 写入频率 × 延时 占用内存（每个最多 16KB）。建议加上限（如配置项）或按连接计数。
5. EPOLLOUT 同时带 EPOLLRDHUP 时丢弃待发数据：对端只是半关闭（`shutdown(SHUT_WR)`）时也会丢；`libhigplat` 不会半关闭，未改。
6. **不同发布者并发写同一 tag**：Board 最终值与订阅者最后收到的事件可能不一致（O1 只保证同一发布者的顺序）。若要求“订阅者最后收到的就是 Board 的最终值”，需要按 tag（可分段加锁）串行化“写 Board + 投递”，并处理好与 getresponse（`StartRequest` 也写 tag）的锁顺序。
