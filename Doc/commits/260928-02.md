# 260928-02 toolgplat 命令上下文与队列操作

需求来源：[Doc/tasks/20260928-02.md](../tasks/20260928-02.md)

## 1. 需求要点

- toolgplat 的命令缺乏上下文：gplat 同时有 Board（唯一的 BOARD）和多个 Queue，命令作用于谁不明确。
- 设想：打开 BOARD 后 `select` / `clear` / `delete` 等作用于 BOARD；打开某个队列后命令作用于该队列；切换对象需要切换上下文。
- 审阅后确认的决策：
  1. Board 始终唯一，只有一个 BOARD。
  2. 队列上下文只允许只读查看，外加 `clear` 和 `write`，不提供会消费数据的 `pop`。
  3. 增加列出服务端已载入队列的命令，`open queue <name>` 的 Tab 补全依赖它。

## 2. 方案审阅结论

| 质疑点 | 结论 |
|---|---|
| 原 `open` 只是本地标志位，不访问服务端 | BOARD 名字写死在客户端，打开 BOARD 仍是本地切换；打开队列必须向服务端读取队列头与类型描述符来校验并获取记录大小 |
| 服务端缺少队列只读接口 | `READHEAD`、`PEEKQ` 在 `statusHandler[]` 中原为 `noop`，需补齐 |
| “读指针 / 写指针处的数据”依赖队列模式 | normal 队列：下一条未读在 `(readPoint+1)%num`，最新写入在 `writePoint`；shift 队列：`readq` 不消费，总是返回 `writePoint`，`readPoint` 只表示是否写入过。工具不暴露指针概念，改为 `peek`（下一次 readq 会返回的记录）与 `last`（最新写入的记录） |
| `readq` 会消费数据 | 工具中不使用，避免抢走真正消费者的数据 |
| 同名命令在不同上下文含义不同（如 `clear`） | 提示符显示当前上下文；破坏性命令保留 `clear all` 显式参数 |
| 部分命令不属于任何上下文 | `conn`、`types`、`help`、`exit`、`create queue` 为全局命令 |
| 名字冲突 | Board 与 Queue 共用 `qbdfile/` 命名空间，`create queue BOARD` 必须拒绝 |
| 写入需要类型化输入 | 新增按字段名赋值的记录解析器 |

## 3. 通信协议与 higplat 库

### 3.1 消息

| MSGID | 处理函数 | 请求 | 响应包体 |
|---|---|---|---|
| `PEEKQ` (17) | `HandlePeekQ` | `qname`，`start` = `PEEK_NEXT` / `PEEK_LATEST`，`datasize` = 记录大小 | `RECORD_HEAD` + 记录 |
| `READHEAD` (23) | `HandleReadHead` | `qname` | `QUEUE_HEAD` |
| `LISTQ` (55，新增) | `HandleListQ` | 无 | 以 `'\0'` 结尾的队列名依次排列，`count` = 队列个数 |

`MSGID` 共 51 个，`statusHandler[]` 中有 22 个有效处理函数。

### 3.2 网络 API（`include/higplat.h`）

- `readhead(sockfd, qname, QUEUE_HEAD*, &error)`
- `peekq(sockfd, qname, position, record, actsize, RECORD_HEAD* /*可为空*/, &error)`，`position` 取 `PEEK_NEXT` / `PEEK_LATEST`
- `listq(sockfd, names, buffsize, &count, &error)`，不含 BOARD

### 3.3 本地 API（`higplat/higplat.cpp`）

- `ReadHead`：对象不是队列时返回 `ERROR_OPERATE_PROHIBIT`（原来会把 BOARD 头当作队列头复制出来）。
- `PeekQRecord`：在队列锁内按模式计算槽位，复制记录头和记录，不移动读写指针；为空时返回 `ERROR_DQ_EMPTY`。
- `ListQ`：持有 `mutex_rw` 遍历哈希表，只列出 `QUEUE_T` 对象。
- `CreateAndLoadQ`：供服务端运行时创建队列（见 5.2）。
- `findtab`：从 `fetchtab` 中抽出的哈希查找，调用者须持有 `mutex_rw`。

### 3.4 反射元数据

- `FieldInfo` 增加 `string_capacity`，为 `PodString<N>` 的 `N`（其他类型为 0），由 `FIELD_DESC_STRING` / `FIELD_DESC_STRING_ARRAY` 通过 `capacity()` 自动填写；其余宏补 `0`。写入字符串字段时据此校验长度，避免 `m_size` 超过容量。

## 4. toolgplat

### 4.1 作用域与命令

`Session` 用 `Scope { Global, Board, Queue }` 取代 `boardOpened`，并保存当前队列的 `QueueContext`（队列名、`QUEUE_HEAD`、类型名、本地 `StructInfo`）。

| 作用域 | 命令 |
|---|---|
| 全局 | `conn`，`open [board]`，`open queue <name>`，`close`，`queues`（新增），`create`，`types`，`help`，`exit` |
| Board | `select`，`delete`，`desc`，`clear all` |
| Queue | `desc`，`peek`，`last`，`clear all`，`write <field>=<value> ...` |

- 提示符：`host>`、`host:BOARD>`、`host:queue/<name>>`。
- `Command` 增加 `scope` 字段，同名命令按作用域分别注册（如 Board 与 Queue 各有 `desc`、`clear`），`FindCommand(name, scope)` 优先匹配当前作用域。
- 命令存在但不在当前上下文时提示可用的上下文，例如：`'clear' is only available in board or queue context. Use 'open board' or 'open queue <queueName>' first.`
- `help` 只列出全局命令和当前上下文的命令；`help <cmd>` 在当前上下文不可用时列出各上下文的同名帮助。
- `create <tag>` 仅在 Board 上下文可用；`create queue` 为全局命令，建好后可直接 `open queue`。
- `open queue` 通过 `readhead` 校验对象并读取队列头，通过 `readtype` 读取记录类型；本地未注册或大小不一致时记录按十六进制显示，且不允许 `write`。
- 队列 `desc` 显示记录类型、模式、槽位数、待读条数（normal）/ 是否有数据（shift）、读写指针、创建时间和字段布局。
- `peek` / `last` 显示记录各字段以及写入时间、来源 IP。
- 命令执行包在 `try/catch` 中，higplat 致命错误码抛出的异常不再导致工具退出。

### 4.2 Tab 补全

- 命令名（及 `help` 后的命令名）按当前作用域补全。
- `open` 后补全 `board` / `queue`；`open queue ` 后实时调用 `listq` 补全队列名。
- 其他位置仍交给 readline 默认的文件名补全。

### 4.3 记录写入（新增 `record_input.h/.cpp`）

- `BuildRecord(StructInfo, assignments, record, error)`：记录先清零，再逐项赋值。
- 字段路径：`name`、`name[i]`、`name.member`、`name[i].member`；非 struct 数组不带下标时按逗号依次赋值。
- 支持 Boolean（true/false/1/0）、Char、各整数类型（`std::from_chars`，拒绝越界与负数赋给无符号）、Single/Double、PodString（按 `string_capacity` 校验，同时写入 `m_size`）。
- `SplitWords` 支持双引号，引号内的空白不切分，如 `location="Room 1"`。

### 4.4 其他

- `type_handle.h` 新增 `kTypeDescriptorBufferSize`、`ParseTypeDescriptor`，`PrintTag` 与队列类型读取共用。
- `display.cpp` 新增 `PrintQueueInfo`、`PrintQueueRecord`，字段布局打印抽成 `PrintStructLayout`（`types` 与队列 `desc` 共用）。
- `toolgplat.vcxproj` 加入 `record_input.cpp/.h`。

## 5. 服务端缺陷修复

### 5.1 队列创建后无法使用、可能覆盖已有文件

| 问题 | 修复 |
|---|---|
| `HandleCreateQueue` 只调用 `CreateQ` 生成文件，不载入，重启服务端后才能使用 | 改用 `CreateAndLoadQ`：创建后立即 `LoadQ` |
| `CreateQ` 会先删除同名文件，网络上 `create queue BOARD ...` 会删掉 BOARD 文件，重建已载入的队列会使服务端映射指向已删除的文件 | 已载入的同名对象（包括 BOARD）一律拒绝，返回 `ERROR_ALREADY_LOAD` |
| 队列名来自网络且未校验，`../config/gplat.conf` 之类的名字会删除并覆盖 qbdfile 目录外的文件 | 校验名字：非空、长度 < 40、不含 `/`、不是 `.` / `..` / `_qbd_file_directory`，否则返回 `ERROR_INVALID_PARAMETER` |
| 并发创建同名队列会互相破坏 | 检查、创建、载入在同一把 `createMutex` 下整体执行 |
| `LoadQ` 假定只在启动时单线程调用，`inserttab` 不加锁 | `LoadQ` 全程持有 `mutex_rw`，改用 `findtab` 查重，避免与 `fetchtab` 并发访问哈希表 |

离线工具 `createq` 仍直接调用 `CreateQ`，保留同名重建的行为。

### 5.2 队列锁失效

| 问题 | 修复 |
|---|---|
| `TABLE_MSG::hMutex` 是 `pthread_mutex_t` 值，`fetchtab` 按值复制，各队列操作锁的是各自的副本，彼此不互斥（`ProcMsgRecvWorkThreadCount = 1` 时不暴露） | `hMutex` 改为 `pthread_mutex_t*`，在 `LoadQ` 中 `new` 并初始化，`UnloadQ` / `UnloadAll` / `LoadQ` 失败路径中销毁并释放；队列函数改为 `pthread_mutex_t& hMutex = *tabmsg.hMutex;` |
| `MulReadQ` 复制记录时完全不加锁 | 加锁 |
| Board 函数中复制了 `hMutex` 但从未使用 | 删除这些局部变量（Board 使用 `pmutex_rw` + `mutex_rw_tag[64]`） |

### 5.3 其他

| 问题 | 修复 |
|---|---|
| `ClearQ` 总是返回 `false`，`clearq` 返回线程上残留的错误码，可能随机报失败 | 成功返回 `true` |
| `clearq` 定义缺少 `extern "C"`，与头文件声明不一致，任何程序调用都会链接失败 | 补上 `extern "C"` |

## 质疑

**1. 现在的 `open` 只是个本地开关，不会访问服务器**

`CmdOpen` 只是把 `boardOpened` 设为 true，所有 `readb/writeb/...` 在客户端里都把 `qname` 写死成 `"BOARD"`。所以"打开 BOARD"只是一道手续，不会检查任何东西。打开 Queue 时情况不同，必须真的问服务器：
- 队列存在吗？是不是真的是 Queue？
- 每条记录多大、是 shift 还是 normal 模式、类型描述符是什么？

这几项是后续显示和写入的前提。**但服务器目前没有注册 `READHEAD`、`PEEKQ` 的处理函数**（`statusHandler[]` 里只有 `READQ/WRITEQ/CLEARQ/CREATEQUEUE`），所以 Queue 上下文要靠服务器补充接口才能成立。

**2. "查看读指针／写指针处的数据"：两种模式下含义不同，而且现有接口做不到**

我看了 `ReadQ`/`PeekQ`：
- normal 模式：下一条未读记录在 `(readPoint+1) % num`，最新写入的在 `writePoint`。`readq` 会移动读指针，**会消费数据**。
- shift 模式：`readq` 不消费，返回 `writePoint` 处的最新记录，`readPoint` 实际上只是"有没有数据"的标志。`PeekQ` 直接拒绝 shift 模式。

所以工具里不能直接把"读指针"这个概念暴露给用户。而且在生产环境里，用 `readq` 去"看一眼"会偷走真正消费者的数据，这很危险。

**3. 同一个命令名在不同上下文里含义不同，有误操作风险**

`clear` 在 Board 里是清空所有 tag，在 Queue 里是清空记录，两个都不可撤销。上下文是隐式状态，用户切换后很容易忘。需要两道防护：
- 提示符必须明确显示当前上下文；
- 破坏性命令保留显式参数，比如 `clear all`。

**4. 不是所有命令都属于某个上下文**

`conn`、`types`、`help`、`exit`、`create queue` 本来就是全局命令。其中 `create queue` 是"创建对象"，不是"在对象里操作"，不应该要求先打开什么，也不应该自动切换过去。

**5. 名字冲突**

Board 和 Queue 都是 `qbdfile/` 下的文件，共用一个命名空间。`create queue BOARD ...` 会和 Board 文件冲突，应该拒绝。`open <name>` 如果不带类型关键字，也会有歧义。

**6. "写入队列数据"缺少输入解析能力**

toolgplat 现在**连 Board tag 的写命令都没有**，只能 `select`。往 Queue 写一条结构体记录，要把命令行文本按类型描述符解析成二进制。这套能力应该和以后的 Board 写命令共用，不能只为 Queue 做一份。另外，`writeq` 会触发 `NotifySubscriber`，会唤醒真正的消费者，帮助说明里要写清楚。

## 方案

### 上下文模型

```
Session {
    conn, host
    enum class Scope { None, Board, Queue } scope
    std::string queueName
    QUEUE_HEAD  queueHead      // 在 open 时取得，desc 时刷新
    std::vector<char> queueType // 类型描述符，用于显示和写入
}
```

- 状态转移：`conn` 之后是 `None`，`open board` 进入 `Board`，`open queue <name>` 进入 `Queue`。
- 在任何上下文里都可以直接用 `open` 切换，`close` 回到 `None`。
- 重新 `conn` 会把上下文重置为 `None`，和现在的行为一致。
- 兼容性：保留不带参数的 `open`，等价于 `open board`。

**提示符**：`127.0.0.1>`、`127.0.0.1:board>`、`127.0.0.1:queue/myq>`。

### 命令表：按作用域注册

给 `Command` 加一个 `scope` 字段。同名命令在不同作用域各注册一条，`FindCommand(name, scope)` 优先匹配当前作用域，再匹配全局命令。好处：
- 每个处理函数只做一件事，不需要 `if (scope == ...)` 分支；
- `help` 只列出当前上下文可用的命令；
- 命令存在但不属于当前上下文时，提示 `'peek' is only available in queue context. Use 'open queue <name>'.`，不再只说 "Unknown command"。

| 作用域 | 命令 |
|---|---|
| 全局 | `conn`, `open board`, `open queue <name>`, `close`, `create queue ...`, `types`, `help`, `exit` |
| Board | `select`, `create <tag>...`, `delete`, `desc`, `clear all` |
| Queue | `desc`（元信息加 read/write 指针和记录数）, `peek`（下一条未读，不消费）, `last`（最新写入）, `clear all`, `write <values...>`, `pop`（显式消费，需要确认） |

`peek`/`last` 在工具里按模式换算槽位，用户不需要关心 `readPoint` 的真实含义。shift 模式下 `peek` 等价于 `last`，或者直接提示不适用。

### 服务器和客户端需要补的接口

按 `add_message_type.md` 的流程：

1. **`READHEAD`**（枚举已有，只缺处理函数）：新增 `readhead(sockfd, qname, QUEUE_HEAD*, &err)`。用于 `open queue` 时校验对象（`qbdtype == QUEUE_T`）以及 `desc`。
2. **按位置只读取记录**：建议新增一个消息，比如 `READQREC(qname, which = NEXT|LATEST|index)`，由服务器在队列锁内计算槽位并复制记录，不移动指针。这样一条消息就覆盖 `peek`、`last` 和以后可能的"按索引查看"，也绕开了现有 `PeekQ` 不支持 shift 模式的问题。只复用 `PEEKQ` 的话，`last` 就没法做。
3. 队列类型描述符用现有的 `readtype(sockfd, qname, "", ...)` 就能取到，`ReadType` 已经支持 `QUEUE_T`，但**现有客户端 `readtype` 把 qname 写死成 `"BOARD"`（`higplat.cpp` 第 3679 行），需要确认或修正**。

### 分阶段实施

1. **重构，不加新功能**：引入 `Scope` 和按作用域的命令表，`open`/`open board`/`close`、提示符、按上下文显示帮助。
2. **服务器补接口**：`READHEAD` 和只读取记录的消息，再加 `open queue` 和 `desc`、`peek`、`last`、`clear all`。
3. **类型化输入解析器**（和 Board 共用），再加队列的 `write`，以及 Board 的 `update <tag> <value>`（顺带补上）。

Searched for regex `pmutex_rw|mutex_rw_tag\[` (`**/higplat/higplat.cpp`), 57 results

有不同用处。两个字段分别给两种对象用：`hMutex` 给队列，`pmutex_rw` 给 BOARD。每个表项实际只会用到其中一个。

| 字段 | 服务对象 | 锁放在哪里 | 保护什么 |
|---|---|---|---|
| `hMutex`（`pthread_mutex_t*`） | 队列（`QUEUE_T`） | `LoadQ` 时在堆上单独创建 | 整个队列的一次操作：读写指针的移动和记录的复制。`ReadQ`、`WriteQ`、`ClearQ`、`PeekQRecord` 等都锁这一把 |
| `pmutex_rw`（`std::mutex*`） | BOARD（`BOARD_T`） | 指向 BOARD 文件映射区里的 `BOARD_HEAD::mutex_rw`（`LoadQ` 里原地构造） | BOARD 的 tag 哈希索引：查找、创建、删除 tag 时遍历或修改索引 |

**BOARD 其实是两级锁**：
1. 先用 `pmutex_rw` 在索引里找到 tag 的位置。
2. 释放它，再按 tag 的哈希值去锁 `BOARD_HEAD::mutex_rw_tag[64]` 中的一把，然后读写数据（见 `ReadB`、`WriteB`）。

这样不同 tag 的读写可以并行，只有查索引那一步是串行的。队列只有一组读写指针，一把整体锁就够了。`mutex_rw_tag` 通过 `pHead` 直接访问，所以没有存进 `TABLE_MSG`。

**实际取值**：
- 队列表项：`pmutex_rw = nullptr`，只用 `hMutex`。
- BOARD 表项：`LoadQ` 也给它创建了一个 `hMutex`，但 BOARD 的函数从来不用（上次删掉的就是这些函数里没用到的副本）。这把是多余的，不会出错，只浪费一个对象。

**为什么一个是 pthread、一个是 std::mutex**：从注释里残留的 `WaitForSingleObject` 和 `ReleaseMutex` 看，这是从 Windows 移植过来的。`hMutex` 原来是 Windows 的互斥量句柄，移植时换成了 `pthread_mutex_t`；BOARD 的锁是后来改写成 `std::mutex` 的。所以风格不统一，不是设计上有意为之。

可以只在队列表项上创建 `hMutex`，BOARD 表项设为 `nullptr`，这样每个表项只持有它真正用到的那把锁。要改的话我来做。
