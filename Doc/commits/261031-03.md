# 20261031-03 gplat 接入保护：fd 耗尽时 accept 不再空转，worker_connections 生效为连接数上限，开启 TCP keepalive

来源：[261031-02](261031-02.md) 第六节“未修改的风险”第 3 条——accept 遇 EMFILE/ENFILE 时忙等。本轮先在隔离 sandbox 里复现并量化，再修复。修复分两层：

- **兜底**：fd 真的耗尽时，epoll 线程不能再空转（预留 fd 拒绝排队连接为主，暂停监听事件为辅，日志限频）。
- **根治**：正常运行时就不让 fd 被用完（`worker_connections` 生效为客户端连接数上限、启动时核对 fd 上限、TCP keepalive 回收死连接）。

| ID | 级别 | 问题 | 旧代码上的复现 |
|---|---|---|---|
| A1 | 高 | accept 遇 EMFILE/ENFILE：连接留在已完成连接队列，水平触发的监听 socket 一直可读，epoll 线程空转并每轮写一条 CRIT 日志；排队的客户端一直收不到应答 | 手工复现：epoll 线程 CPU 99.9%，日志写入 81 MB/s，3 秒轮转约 233 次；`conn.emfile_rejects_pending`：10 个连接挂起、CPU 100%、EMFILE 日志 41395 行 |
| A2 | 中 | `worker_connections` 只是连接池初始大小，池不够就扩，客户端连接数实际只受 RLIMIT_NOFILE 限制 | `conn.max_connections_enforced`：超出上限的 100 个连接全部被正常接受 |
| A3 | 中 | 不核对进程 fd 上限是否容得下 `worker_connections`（systemd 服务缺省软上限通常是 1024） | `conn.fd_limit_clamps_max_connections`：没有连接上限，也没有告警 |
| A4 | 中 | 没有 keepalive / 空闲超时：掉电、拔网线的客户端留下的连接（服务端从不主动发数据时）永不回收，逐渐耗尽 fd | `conn.keepalive_configured`：服务端 socket 上没有 keepalive 定时器 |

原则不变：外科手术式修改；线协议不变；锁顺序不变；新增的接入状态只在 epoll 线程访问（连接计数为原子量）。合法客户端唯一可见的变化是连接数超限时被立即断开（见第三节）。

## 一、A1：accept 遇 EMFILE/ENFILE 时忙等

### 机理

1. 监听 socket 以 `EPOLLIN | EPOLLRDHUP` 注册，没有 `EPOLLET`，是水平触发（`ngx_epoll_init`）。
2. Linux 的 `accept` 先分配 fd 号、再从已完成连接队列取连接。分配 fd 失败（EMFILE 进程级 / ENFILE 系统级）时直接返回，**连接不出队**，监听 socket 保持可读。为新连接分配 socket 时内存不足（ENOBUFS/ENOMEM）若发生在出队之前也一样。
3. worker 主循环 `epoll_wait(-1)` 立即返回 → `ngx_event_accept` → `accept4` 失败 → 写一条 CRIT 日志（CRIT=3，配置 `LogLevel = 8`、代码缺省 6，都会写）→ EMFILE 分支原样 return（注释里写了 nginx 的做法但没实现）→ 回到 `epoll_wait`。

### 实测（修复前）

隔离 sandbox，`ulimit -n 64`，日志配置与仓库一致（轮转 3 个、每个 1MB），52 个客户端把 fd 用完，其中 3 个停在队列里：

| 阶段 | epoll 线程 CPU | 日志写入 | gplat.log 轮转 |
|---|---|---|---|
| 空闲 | 0% | 0 | 0 |
| fd 耗尽、3 个连接排队（3 秒） | 99.9% | 81 MB/s（约 75 万行/秒，每行 109 字节） | 约 233 次 |
| 客户端关闭 5 个连接后 | 0% | 0 | 0 |

- 单核被占满，直到有 fd 释放才自愈。
- 日志：有轮转兜底，磁盘不会写满（261031-02 中“可能写满磁盘”只在关闭轮转 `LogRotateFileCount <= 0` 时成立，那时约 80 MB/s 写盘）。但 4 个日志文件只装得下约 40 ms 的内容：实测 3 秒后只剩 31,629 行同一条 CRIT，启动日志全被冲掉，事后无从查起是谁耗尽了 fd。
- 客户端：三次握手由内核完成，`connectgplat` 成功；第一个请求一直等下去（libhigplat 没有接收超时；服务端没读到请求，`waitpostdata`/`getresponse` 的服务端超时也不会启动）。backlog（511）满后新 SYN 被丢弃，表现为 `connectgplat` 2 秒超时。已建立的连接仍能收发，但要与空转线程争 CPU 和日志锁。

### fd 为什么会被用完

- 没有连接数上限（A2）：唯一的上限是 RLIMIT_NOFILE，systemd 服务未配 `LimitNOFILE` 时软上限通常是 1024，约 1000 个连接就触发。
- 没有 keepalive（A4）：客户端掉电、拔网线时服务端收不到 FIN/RST；只做请求/应答、服务端从不主动发数据的连接一直处于 ESTABLISHED，客户端每重启重连一次就多占一个 fd。客户端重连时不 `disconnectgplat` 也是同样效果。

## 二、修复思路

### 2.1 兜底：预留 fd 为主、暂停监听为辅（A1）

可选的做法：

| 做法 | 效果 | 问题 |
|---|---|---|
| 监听 socket 改边缘触发 | 不再空转 | 失败后不再有通知，排队连接要等下一个新连接到来才会被再次尝试，没有新连接就一直卡住 |
| 暂停监听事件、定时恢复（nginx） | 不再空转 | 排队的客户端仍然挂着，而 libhigplat 没有接收超时 |
| 预留 fd（libuv、muduo） | 腾出名额把排队连接取出立即关闭，客户端马上失败、走重连 | 腾出的名额可能被别的线程或进程抢走（ENFILE 时尤甚）；内存不足时帮不上 |

所以以预留 fd 为主、暂停为辅，由 `ngx_accept_exhausted` 处理：

1. worker 初始化时打开 `/dev/null`（`O_RDONLY | O_CLOEXEC`）作预留 fd。
2. EMFILE/ENFILE：关掉预留 fd，循环 `accept` + `close`，一次最多 `NGX_ACCEPT_DRAIN_MAX`（64）个；`EAGAIN` 表示队列已清空，`ECONNABORTED`/`EINTR` 跳过；之后重新打开预留 fd。取满一批也算有进展，剩下的留给下一轮 epoll。
3. 既没清空队列也没取满一批（预留 fd 已用掉、腾出的名额被抢走或号不小于软上限），以及 ENOBUFS/ENOMEM：暂停所有监听 socket 的读事件 `NGX_ACCEPT_PAUSE_MS`（500 ms，与 nginx 的 `accept_mutex_delay` 缺省值相同）。暂停用 `EPOLL_CTL_MOD` 把事件掩码置 0（`ngx_epoll_oper_event` 的 DEL 分支本是空实现），保留注册和 `data.ptr`；监听 socket 不会报 ERR/HUP，掩码为 0 即完全静默。
4. 恢复：`ngx_epoll_process_events` 每次 `epoll_wait` 之前调用 `ngx_accept_wait_timeout(timer)`。暂停期间把等待时间限制在剩余时长内；到期后补开预留 fd、恢复监听事件；恢复失败（如内核内存不足）则保持暂停、稍后再试，否则监听 socket 会永远收不到新连接。全部在 epoll 线程完成，不需要定时器线程，也不需要额外的锁。
5. 预留 fd 丢失后，下一次成功 accept 时补开。
6. 日志限频（`LogThrottle`）：首条立即记，之后每 `NGX_LOG_THROTTLE_SEC`（5 秒）最多一条，并带上期间被抑制的次数；内容包含拒绝的连接数、是否暂停，以及 errno 文本。

### 2.2 根治一：`worker_connections` 生效为客户端连接数上限（A2）

- 语义沿用配置文件里原有的注释：客户端连接上限 = `worker_connections` − 监听端口数（与 nginx 一致，监听 socket 也占一个连接对象）。
- 计数 `m_onlineUserCount`（原子）：`ngx_event_accept` 中 epoll 注册成功后 +1，`ngx_close_and_recycle` 中 −1。后者是已建立连接唯一的关闭路径；accept 早期失败走 `ngx_close_connection`，那时还没有计数。
- 超限：accept 后立即 close。不 accept 的话连接留在队列里，就会重蹈 A1；立即关闭则客户端马上读到 EOF，按连接错误处理。拒绝日志同样限频。
- 计的是持有 fd 的连接。已关闭、在回收队列里等宽限期的连接对象不占 fd，不计入；所以高频 churn 时连接池对象数仍可能超过 `worker_connections`（既有特征化 M1，未改）。

### 2.3 根治二：启动时核对 fd 预算（A3）

`ngx_init_accept_limits()` 在 worker 的 `ngx_epoll_init()` 末尾调用，此时固定占用的 fd（标准输入输出、日志、监听、epoll、定时器、预留 fd 等）都已打开：

```
used = /proc/self/fd 中的条目数
need = used + NGX_FD_SPARE(16) + 客户端连接上限
软上限 < need：在硬上限以内抬高软上限（setrlimit，记 NOTICE）
仍然 < need：  客户端连接上限 = 软上限 − used − 16（至少 1），记 WARN，提示调大 ulimit -n / LimitNOFILE
```

余量 16 留给日志轮转、CREATEQUEUE 建文件、超限时临时 accept 再关闭等。启动日志总会记一行“客户端连接上限N（worker_connections=…，RLIMIT_NOFILE=…，已打开fd …）”。放在 worker 而不是 master：rlimit 按进程生效，fd 也是在 worker 里用、在 worker 里数。

### 2.4 根治三：TCP keepalive（A4）

- 新配置项 `Sock_KeepAlive`（1）、`Sock_KeepAliveIdle`（60 秒）、`Sock_KeepAliveInterval`（10 秒）、`Sock_KeepAliveCount`（6 次）：死连接约 60 + 10 × 6 = 120 秒后被回收。取值超出内核允许的范围（32767 / 32767 / 127）时回退缺省值并告警；`Sock_KeepAlive = 0` 关闭。
- 每个 accept 的连接先设 `TCP_KEEPIDLE`/`TCP_KEEPINTVL`/`TCP_KEEPCNT`，再开 `SO_KEEPALIVE`（`ngx_set_keepalive`）。
- 探测失败时内核以 ETIMEDOUT 终止连接，epoll 报可读、`recv` 出错，走既有的 `ngx_close_and_recycle` + 断连清理，不需要新的关闭路径。
- 对端主机只要还在，内核就会应答探测，与应用是否空闲、是否阻塞在 `waitpostdata` 无关；周期探测还能维持中间 NAT/防火墙的会话状态。
- 没加 `TCP_USER_TIMEOUT`：有未确认数据的死连接已由重传超时（约 15 分钟）兜底，而且它与 keepalive 的交互较复杂。

## 三、对客户端和部署的影响

- 连接数超限：`connectgplat` 照常返回 fd（握手由内核完成），服务端随即关闭，之后第一个调用以 CONNECTION 类错误失败——按断线处理，`disconnectgplat` 后稍后重连（已写入 `Doc/api_reference.md`）。
- 缺省 `worker_connections = 1024` 即最多 1023 个客户端；超过的部署要同时调大它和 fd 上限。
- 网络中断超过约 2 分钟：服务端会断开这些连接；阻塞在 `waitpostdata(-1)` 的客户端要到下一次发请求才会发现（libhigplat 目前没有 keepalive / 接收超时，见第五节）。
- 新增日志，便于运维检索：

| 级别 | 日志 | 含义 |
|---|---|---|
| NOTICE | `客户端连接上限N（worker_connections=…，RLIMIT_NOFILE=…，已打开fd …）` | 启动时确定的连接上限 |
| NOTICE | `RLIMIT_NOFILE软上限A抬高到B` | 启动时抬高了软上限 |
| WARN | `进程可打开文件数上限RLIMIT_NOFILE=…不足以支持worker_connections=…，客户端连接上限降为N…` | fd 上限不够，连接上限被降低 |
| WARN | `客户端连接数已达上限N，拒绝新连接（上次记录后另拒绝K个）` | 连接数超限（5 秒最多一条） |
| CRIT | `…accept4()失败，fd或内存耗尽：已拒绝N个排队连接[，暂停接受新连接]…` | fd 或内存耗尽（5 秒最多一条） |
| WARN | `配置项Sock_KeepAlive…超出范围…，改用缺省值…` | keepalive 配置非法 |

## 四、测试

### 测试框架

- `ServerConfig::nofile`：exec 前把 gplat 的 RLIMIT_NOFILE 软/硬上限都设为该值。
- `ServerConfig::extraConf`：向 gplat.conf 追加配置行。解析器取同名项第一次出现的值，所以只能用于 fixture 没写出的配置项。
- `ServerFixture::log_path()`：sandbox 中 gplat 日志的路径。

### 新增 `test_accept.cpp`（5 个用例，`TAG_CONN`，进入常规 `make test`）

| 用例 | 做法 | 旧代码 | 新代码 |
|---|---|---|---|
| `conn.max_connections_enforced` | `worker_connections=9`（8 个客户端）：8 个连接正常服务；再连 100 个，必须被立即关闭；拒绝日志 1～2 行；断开一个后名额恢复 | 100 个全被接受（每个都等满 2 秒） | 100 个在 9 ms 内全被关闭 |
| `conn.fd_limit_clamps_max_connections` | `nofile=64`：日志里的连接上限低于 48 且有告警；上限内都能服务，多一个被立即关闭；全程没有 EMFILE | 没有连接上限日志 | 上限 26，通过 |
| `conn.emfile_rejects_pending` | 启动后用 `prlimit` 压低 worker 的软上限，恰好留 6 个空闲 fd 号：前 6 个连接被服务，之后的被立即关闭而不是挂起；epoll 线程 CPU < 20%；EMFILE 日志 1～2 行；释放连接后恢复 | 10 个连接挂起，CPU 100%，EMFILE 日志 41395 行 | 6 个服务、6 个被拒、0 个挂起，CPU 0% |
| `conn.emfile_total_exhaustion_pauses` | 软上限压到预留 fd 的号上（预留 fd 是唯一带 `O_CLOEXEC` 的 `/dev/null`，从 `/proc/<pid>/fdinfo` 识别），腾出的号也用不上：请求得不到应答，但 CPU < 20%，日志限频且出现“暂停接受新连接”；恢复软上限后 2 秒内重新接受连接 | 找不到预留 fd（前置条件失败） | 通过，CPU 0% |
| `conn.keepalive_configured` | `Sock_KeepAliveIdle=40`：从 `/proc/net/tcp` 读服务端 socket 的定时器，`tr=2`（已建立连接上的 sk_timer 只用于 keepalive），剩余时间在 30～40 秒；`Sock_KeepAlive=0` 时 `tr=0` | `tr=0` | `tr=2`，剩余 3980 个时钟滴答（39.8 秒） |

两个 EMFILE 用例只压低软上限：非特权进程压低硬上限后就抬不回来，只动软上限才能在用例结束前恢复。

### 调整 `race.subscribe_close_no_stale`

原用例 `worker_connections=4`，却同时开约 33 个连接（32 个探针 + 发布者），靠的是连接池可以扩张；上限生效后多出的连接会被拒绝。现改为 `worker_connections = kProbes + 2`（监听 socket + 发布者 + 32 个探针），发布者最先连上，不与探针争抢受害连接用过的对象。空闲表先进先出，探针要取尽整个连接池才能保证复用到每个受害连接用过的对象。临时在 accept 处打日志核对：24 个受害连接用过的对象全部被探针复用，覆盖面与原用例一致。

## 五、未处理

- libhigplat 没有 keepalive 和接收超时：服务端不应答时（暂停兜底期间、网络中断后服务端已断开的半开连接）客户端会一直等。需要在客户端加，涉及 API 语义，本轮未动。
- 未设 `TCP_USER_TIMEOUT`（理由见 2.4）。
- 连接池按峰值扩张、不收缩（M1）仍在，只是不再影响 fd。
- 261031-02 第六节的其余风险（getresponse 迟到响应错配、worker 崩溃不重启、超时无上限等）不在本轮范围。
