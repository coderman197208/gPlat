# 20261031-01 gplat 稳定性审阅：修复 CREATEQUEUE 远程可触发崩溃，加固发送路径与连接回收

本轮不是功能开发，而是针对服务端稳定性的一次严格代码审阅。gplat 为众多客户端提供实时订阅与读写服务，需要频繁建立/断开连接、分配/回收内存，并涉及多把锁和定时器等异步机制；任何细微漏洞都可能让 worker 进程崩溃。审阅发现并修复了 **1 个远程可触发的崩溃缺陷** 和 **3 处潜伏的生命周期/内存安全隐患**。

原则是外科手术式修改：只动有问题的代码，合法客户端（`libhigplat`）看到的行为不变，不做无关重构。

## 一、关键缺陷：CREATEQUEUE 远程可触发 SIGFPE（整台服务下线）

### 现象与复现

客户端 API [`createqueue`](../../higplat/net_client.cpp)（`net_client.cpp:467`）本就拒绝 `recordnum<=0`，**但该校验只在客户端侧**。服务端 `HandleCreateQueue → CreateAndLoadQ → CreateQ` 没有相同的校验。裸 TCP 客户端、第三方语言绑定、或畸形报文只要直接发一个 `count=0` 的 `CREATEQUEUE`，服务端就会**成功建出一个 `num==0` 的队列并返回 `error=0`**。

此后任何 `WRITEQ` / `PEEKQ(PEEK_NEXT)` / `IsFullQ` 都会计算 `% head->num`，即 `% 0` → **整数除零 → SIGFPE**，worker 进程被杀死；master 随即收到 `SIGCHLD`、把 `g_stopEventMain` 置 1 并退出 → **整台服务下线**。

在隔离 sandbox 中用裸协议复现（绕过客户端校验）：`CREATEQUEUE(count=0)` 返回 `error=0`（队列已建），紧接一个 `WRITEQ` 得到空响应（连接被断）。内核日志确认：

```
traps: gplat[...] trap divide error ... in libhigplat.so
gplat: potentially unexpected fatal signal 8.
```

### 根因

- `num` 在队列创建时写入、运行期从不改变，而 [`local_queue.cpp`](../../higplat/local_queue.cpp) 中 9 处 `% head->num`（readq/writeq/peekq/mulreadq/isfullq 等）都隐式依赖 `num>0`。
- [`CreateQ`](../../higplat/local_queue.cpp)（`local_queue.cpp:91`）只校验了 `recordSize > GPLAT_MAX_DATA_SIZE || typeSize > TYPEMAXSIZE`，**没有下界校验**；`createq` CLI 是在 `main()` 里挡掉 `size==0 || number==0` 的，这条不变式没有落到库函数里，服务端直接调库就绕过了它。
- 另外 `recordNum` 无上界：超大 `count` 会让 `CreateQbdFile` 对多 GB/TB 的 mmap 做 `memset`，磁盘写满时触发 SIGBUS，同样是崩溃面。

### 修复

集中在 [`higplat/local_queue.cpp`](../../higplat/local_queue.cpp)：

1. **`CreateQ` 补齐服务端校验**（`local_queue.cpp:91`）：拒绝 `recordSize<=0`、`recordNum<=0`、`typeSize<0`；文件尺寸改用 64 位计算避免溢出，并以 `kMaxQueueFileSize = 1 GiB`（`local_queue.cpp:14`）为上限，拒绝超大 `recordNum`，防止多 GB/TB 分配导致磁盘写满/SIGBUS。非法参数返回 `ERROR_PARAMETER_SIZE`。
2. **`FetchQueue` 纵深防御**（`local_queue.cpp:27`）：所有队列操作都经由 `FetchQueue` 取 `head`，在此统一拦截 `num<=0 || size<0` 的队列（非法创建或文件损坏遗留），返回 `ERROR_OPERATE_PROHIBIT`。这样即使历史上已有坏文件被载入，任何 `%num` 路径也不会再除零。

修复后，`count=0/-5/INT32_MAX`、`recsize=0/-1` 等全部以 `ERROR_PARAMETER_SIZE` 被拒，worker 与 master 均存活；合法队列的 create/write/read 不受影响。

## 二、发送路径与连接回收的三处加固

以下三处是审阅中发现的潜伏隐患，触发概率低（受 20 秒延迟回收、单线程 accept 等现有设计缓解），但在"任何崩溃都不可接受"的场景下仍应彻底消除。

### 1. 发送路径悬垂 `psendbuf`（潜在 use-after-free）

[`ngx_write_request_handler`](../../gplat/ngx_c_socket_request.cxx)（`ngx_c_socket_request.cxx:313`）里，当 `sendproc()` 返回 `0`/`-2`（对端已断开）时，收尾代码释放了 `psendMemPointer` 并置空，却把 `psendbuf`/`isendlen` 留成指向已释放内存的悬垂指针，而 `EPOLLOUT` 仍挂在 epoll 上。若断开后又有一次"干净的" `EPOLLOUT` 重新进入本函数，`sendproc(pConn, psendbuf, …)` 就会读已释放内存；重复进入还会把 `iThrowsendCount` 减成负数。

修复：
- 持 `sendMutex` 后加**重入守卫**（`ngx_c_socket_request.cxx:320`）：`iThrowsendCount<=0 || psendMemPointer==NULL` 时直接返回，绝不再 `sendproc` 或再次 `--iThrowsendCount`。
- 收尾释放时一并令 `psendbuf=NULL; isendlen=0`（`ngx_c_socket_request.cxx:359`）。
- 把"释放发送缓冲即失效 `psendbuf`"这条不变式扩展到另外两个释放点——[`ngx_close_and_recycle`](../../gplat/ngx_c_socket_conn.cxx)（`ngx_c_socket_conn.cxx:231`）和 `ngx_epoll_process_events` 的 EPOLLOUT 错误分支（`ngx_c_socket.cxx:783`）——使 `psendMemPointer==NULL ⟹ psendbuf 失效` 在所有路径上成立。

### 2. `ngx_close_connection` 归还后再读 `fd`（顺序错误）

[`ngx_close_connection`](../../gplat/ngx_c_socket_conn.cxx)（`ngx_c_socket_conn.cxx:329`）先调用 `ngx_free_connection(pConn)`（把连接对象放回空闲池、可被复用），**之后**才读 `pConn->fd` 去 `close`。虽然当前只有 accept（单线程 epoll 主线程）消费空闲池、实际不会并发复用，但顺序本身是错的。

修复：先用本地变量 `int fd = pConn->fd` 保存并 `close(fd)`，再 `ngx_free_connection(pConn)`，日志也用本地 `fd`。

### 3. 断开后迟到投递串扰（`m_bWaitingPost` 未复位）

连接断开时 [`ngx_cleanup_closed_connection`](../../gplat/ngx_c_socket_request.cxx)（`ngx_c_socket_request.cxx:28`）复位了 `m_bWaitingTimeout`，却没复位 `m_bWaitingPost`。设想一个正阻塞在 `waitpostdata` 的连接断开：其它线程的 `NotifySubscriber` 若持有断开前的订阅快照、在 cleanup 之后落到这个连接对象上，会看到 `m_bWaitingPost` 仍为真 → 走 `msgSend`。而该连接对象的 `fd` 号可能已被新连接复用，于是把订阅事件发到了无关的新客户端上（串扰）。

修复：在 `ngx_cleanup_closed_connection` 中持 `logicPorcMutex` 复位 `m_bWaitingPost=false`（`ngx_c_socket_request.cxx:41`）。这样迟到投递会走 `EnqueuePost`（随对象回收一并释放），而不是发到复用的 fd 上。

> 为什么只在 cleanup 复位就够：旧连接对象本身在回收队列里要等 20 秒才可能被重新 `GetOneToUse`，`NotifySubscriber` 用的正是这个旧对象；`close_and_recycle` 到 cleanup 之间 accept 线程正忙于 recv 流程、无法接受新连接，fd 号不会在这个窗口内被复用。因此 cleanup 复位后，旧对象在整个回收期内 `m_bWaitingPost` 恒为假。

## 三、不变的部分

- **线协议**：`MSGHEAD` 布局、`MSGID`、各消息字段与应答格式不变。
- **锁规则**：`logicPorcMutex → sendMutex → m_sendMessageQueueMutex` 的顺序不变；发送积压/EPOLLOUT 续发、连接延迟回收（20s）等机制不变。
- **合法路径**：`CreateQ` 对合法参数（`recordSize∈[1, 16384]`、`recordNum≥1` 且文件 ≤1 GiB）行为不变；发送路径的正常部分发送/积压排空逻辑不变。
