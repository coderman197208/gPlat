## 原因

这次失败来自测试本身的计时竞态，不是服务器的问题。服务器没有连接上限，也没有 fd 泄漏。

我单独把 `stress.concurrent_connections` 跑了 5 次，1 次失败（fd 21 → 141），4 次通过（fd 峰值 221 = 21 + 200）。结果不固定，说明是时序问题。

**失败过程：**

1. 每个客户端线程在 `connectgplat()` 返回后就执行 `++ready`（`test_stress.cpp`）。
2. 但 `connectgplat` 只要内核完成三次握手就返回，此时连接还在 listen 的已完成队列里，服务器可能还没调用 `accept`。worker 进程只有在 `accept` 之后才多出一个 fd。
3. 服务器端的 `ngx_event_accept` 在 LT 模式下每次 `epoll_wait` 只 `accept` 一个连接，后面还要做 `ngx_get_connection` 和 `epoll_ctl`。200 个线程在 12 核上并发 connect，单个 epoll 线程按顺序逐个 accept，跟不上。WSL2 的系统调用开销更大，差距更明显。
4. 主线程看到 `ready == 200` 后立刻采样 `/proc/<worker>/fd`（`test_stress.cpp` 到第 119 行）。这时你那次运行里服务器只 accept 了 112 个（16 → 128），所以第 132 行的检查失败。

**说明服务器没问题的依据：**
- 同一用例中 `completed == 200 × 1000` 等其他检查都通过了，说明 200 个连接最后都被正常服务。
- 结束后 fd 回到基线（16 → 16），没有泄漏。
- 资源限制都够：`somaxconn = 4096`，`ulimit -n` 很大，`worker_connections = 1024`。

## 建议修复（只改测试，还没动代码）

采样前轮询等待服务器把队列里的连接都 accept 完，设一个超时，不要只采一次：

```cpp
bool allReady = ready.load() == clients;
bool sampled = false;
int held = -1;
// connect() 返回只代表握手完成，worker 的 accept 可能尚未追上；等待 fd 数到位。
const uint64_t acceptDeadline = now_nanos() + 2000000000ull;
do {
    sampled = sampler.tick();
    held = sampler.fd_last();
    if (!sampled || held >= baseline + clients - 2) break;
    usleep(1000);
} while (now_nanos() < acceptDeadline);
```

这样修改后，第 132 行的断言测的才是"服务器确实同时持有 200 个连接"。附带影响是 `sampler.report` 里的样本数会变多，这个用例没有对它做断言。

另外可以考虑改服务器：让 `ngx_event_accept` 循环 accept 直到 `EAGAIN`（类似 nginx 的 `multi_accept`）。这能加快建连，但消除不了这个竞态，所以测试仍然要改。
