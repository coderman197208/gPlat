**故障结论**

这是 gPlat 服务端构造 `timer_500ms` 通知时，`error` 字段未初始化导致的误报，与 Snap7 或 PLC 通信无关。

完整触发链：

1. 写线程订阅 `timer_500ms`，用于定期唤醒并检查退出状态。
2. gPlat 在 `ngx_c_slogic.cxx:698` 的 `NotifyTimerSubscriber()` 中分配通知缓冲区。
3. 缓冲区通过 `AllocMemory(..., false)` 分配，`false` 表示不清零，见 `ngx_c_memory.cxx:14`。
4. 定时通知只设置了 `id`、`itemname` 和 `bodysize`，遗漏了：
   ```cpp
   pPkgHead->error = 0;
   ```
5. 客户端 `higplat.cpp:1460` 的 `waitpostdata()` 无条件读取这个未初始化的 `error` 字段。只要残值非零且不是 `ERROR_WAIT_TIMEOUT`，函数就返回 `false`。
6. `threadWritePlc.cpp:326` 将所有 `false` 都解释为连接故障，因此打印：
   ```text
   waitpostdata failed, error = 132017, reconnecting gPlat...
   ```

`132017` 不在项目定义的错误码范围内。gPlat 自定义错误码目前是 `1001..1043`，所以它只是堆内存中的随机残值。启动后约 22 秒才出现，是因为之前分配到的内存碰巧为零；这不是固定的 22 秒超时。

作为对照，普通 tag 通知和 PLC 通知都明确执行了 `pPkgHead->error = 0`，只有定时通知分支遗漏了这一句。

**连带问题**

这次误判还会造成连接泄漏：

- `waitpostdata()` 收到非零业务错误时不会关闭旧 socket。
- 写线程直接用新 fd 覆盖 `conn`，没有先执行 `disconnectgplat(conn)`。
- 因此日志中的旧 `fd=11` 很可能仍然存活，随后又创建了 `fd=15`。
- 旧连接的 `timer_500ms` 订阅也不会被取消，服务端会不断为无人读取的旧连接积压定时事件，长期运行可能造成 fd 和内存持续增长。

**建议修复顺序**

1. 在 `NotifyTimerSubscriber()` 中明确设置 `pPkgHead->error = 0`。更稳妥的方式是将整个生成的 `PKGHEAD` 清零后再赋值。
2. `waitpostdata()` 应验证 `readn()` 是否完整读到 `sizeof(MSGHEAD)`，并校验响应 `id` 和 `bodysize`。
3. 写线程进入重连前关闭旧 fd，且检查 `subscribe()`、`registertag()` 的返回值。
