# 20261031-04 gplat 客户端时长加服务端上限：在途延时投递计入每连接上限，断开即释放

来源：[261031-02](261031-02.md) 第六节“未修改的风险”第 4 条——超时/延时没有服务端上限。

逐项核对后，三者风险不同：

| 项 | 修复前 | 内存是否有界 |
|---|---|---|
| waitpostdata 超时 | 每连接至多一个超时定时器（新等待取代旧等待），不带事件包 | 有界 |
| getresponse 超时 | 拒绝 `<= 0`；每个 request_tag 最多排 64 个，请求方断开时 `CancelRequest` 释放 | 有界 |
| **POST_DELAY 延时** | 每次写为每个延时订阅挂一个带完整事件包（≤16KB）的定时器；不计入 `Sock_MaxPendingPost`，断开后也不取消，到期才释放 | **无界** |

另一个问题：`TimerManager::add_once` 的参数是 `uint64_t`，客户端传来的负数会回绕。负的 POST_DELAY 延时按机器已运行时长不同，要么立即触发、要么永不触发（事件包占到进程退出）；`subscribedelaypost` 不检查 `delaytime`。裸协议的 `POSTWAIT timeout < -1` 同样回绕（libhigplat 会拦截，裸协议可绕过）。

POST_DELAY 的语义保持不变：每次写各自延时投递一次，不做防抖/合并（用来代替客户端 sleep）。

| ID | 级别 | 问题 | 旧代码上的复现 |
|---|---|---|---|
| D1 | 中 | 在途延时投递不受每连接上限约束，内存按 写入频率 × 延时 × 订阅数 增长 | `pubsub.delaypost_capped`（上限 10，延时内写 25 次）：投递 16 条且序号错乱 |
| D2 | 中 | 订阅方断开后在途延时投递要等到期才释放；停机时直接泄漏 | `pubsub.delaypost_freed_on_disconnect`（ASan）：LSan 报 9040 bytes / 20 blocks |
| D3 | 低 | POST_DELAY 延时为负或过大、POSTWAIT `timeout < -1`、getresponse 超时过大均被接受 | `pubsub.delaypost_invalid_delay`、`pubsub.postwait_invalid_timeout`：服务端返回成功 / WAIT_TIMEOUT |

## 一、在途延时投递计入每连接上限（D1、D2）

- `ngx_connection_s` 新增 `m_delayedPosts: key → {TimerId, postbuf}`（`logicPorcMutex` 保护），key 取全局递增的 `s_nextDelayedKey`，连接对象复用后也不会重号。
- `NotifySubscriber` 的 POST_DELAY 分支：`HasPostRoom()`（`m_listPost` 与 `m_delayedPosts` 合计 < `Sock_MaxPendingPost`）不满足时经 `DropPost` 丢弃最新事件（与普通待发队列同一条限频日志）；否则挂定时器并登记。登记在持有 `logicPorcMutex` 期间完成，回调要先拿到这把锁，不会早于登记查表。
- 到期回调 `CLogicSocket::OnDelayedPost`：持锁按 key 取走后 `DeliverPostLocked`；找不到 key 说明连接已清理且清理时没能取消本定时器，由回调释放事件包。
- `ClearPostList`（断开清理、连接分配/回收时调用）：对每个在途延时投递 `g_tm.cancel`，成功则就地释放；失败说明回调已开始执行（正等本锁），留给回调释放。符合 `TimerManager::cancel()` 不等待回调的约定，每个事件包恰好释放一次。
- 锁顺序不变：`logicPorcMutex` → 定时器内部锁（`StopTimeoutTimer` 早已如此）；定时器线程执行回调时不持内部锁。
- 效果：每连接内存上界为 `Sock_MaxPendingPost` × 事件包大小，与普通待发队列一致；断开即释放。

## 二、入口校验（D3）

| 请求 | 合法范围 | 越界 |
|---|---|---|
| SUBSCRIBE（POST_DELAY）`eventarg` | `[0, Sock_MaxPostDelay]`，默认 300000 ms | `ERROR_INVALID_PARAMETER`，不登记订阅 |
| POSTWAIT `timeout` | `>= -1`（-1 无限等待，不设上限：每连接只有一个不带数据的定时器） | `ERROR_INVALID_PARAMETER`，不改变当前等待状态 |
| GETRESPONSE `timeout` | `[1, Sock_MaxRequestTimeout]`，默认 300000 ms | `ERROR_INVALID_PARAMETER` |

- 新配置项 `Sock_MaxPostDelay`、`Sock_MaxRequestTimeout`（`<= 0` 按默认值），在 `CSocekt::ReadConf` 读取。
- libhigplat `subscribedelaypost` 本地拒绝 `delaytime < 0`；上限只有服务端知道，由服务端判定。

兼容性：线协议不变。超过 5 分钟的延时订阅或 getresponse 超时会被拒绝，需要时调大配置。
