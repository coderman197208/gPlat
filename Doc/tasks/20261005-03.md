# 20261005-03 客户端错误处理重构：错误分类 + 错误钩子 + GplatConnection 按类别抛异常

本轮评审了 `libhigplat` 的错误检测与抛出方式（`AutoErrorCheck` 拦截器 + `IsFatalError` + `GplatConnection` 抛异常），提出 4 项改进，实施了前 3 项。第 4 项（C 库关闭调用方持有的 fd）尚未处理，见第六节。

| 项 | 内容 | 状态 |
|---|---|---|
| 1 | 修正错误分级：errno 归为连接错误、修正 `ERROR_SOCKET_NOT_CONNECTED`、区分两个"缓冲区太小" | 已完成（随后被第 3 项的分类取代） |
| 2 | 库内 `std::cout` 打印改为可替换的错误钩子，去掉重入计数 | 已完成 |
| 3 | 按错误类别（而不是逐个错误码标 Fatal）决定 `GplatConnection` 是否抛异常 | 已完成 |
| 4 | C 库在出错时 `close()` 调用方持有的 fd，fd 所有权不清 | **未处理** |

## 〇、评审结论（改动前的问题）

改动前：每个网络 API 首行声明 `AutoErrorCheck _checker(error)`，析构时若错误码为 Fatal 级就 `std::cout` 打印一行；`GplatConnection` 用 `IsFatalError` 判断后抛 `std::runtime_error`。异常不穿过 `extern "C"` 边界、策略放在调用方编译单元，这两点是合理的。问题：

1. **分级是错误码的静态属性，与调用场景无关。** `ERROR_TAG_NOT_EXIST` 被标为 Fatal，`GplatConnection::readb` 读不存在的 tag 会抛异常；而探测 tag、删除已删的 tag 等场景下这是正常分支。方法同时返回错误码又可能抛异常，调用方要查表才知道某个码走哪条路。
2. **严重程度倒置。** 断线（errno，库已 `close(fd)`）落到 `GetErrorInfo` 的 `default`，被当作 Ignore（"unknown error"），既不打印也不抛异常；`ERROR_SOCKET_NOT_CONNECTED` 被封装类使用却标为 Deprecated、描述为空；`BUFFER_TOO_SMALL`（Ignore）和 `ERROR_BUFFER_TOO_SMALL`（Fatal）描述相同、级别不同。
3. **库里直接 `std::cout`。** 写到 stdout 而非 stderr；调用方无法关闭、重定向或限频；多段 `<<` 在多线程下会交错；toolgplat 自己已打印错误码，库再打一行；`GplatConnection` 用户拿到异常后还会看到一次打印。
4. **`g_api_depth` 重入计数没必要。** 嵌套只发生在导出函数转调内部 helper（`writeb` → `writeb_`、`write_plc_*` → `writeb_plc` 等），把拦截器只放在导出函数即可。
5. **C 库关闭调用方的 fd**（第 4 项，见第六节）。

## 一、错误分类（第 1、3 项）

### 修改

第 1 项先给原来的 `ErrorLevel` 增加了 Connection 级；第 3 项再把"级别"整体换成"类别"。第 1 项新增的 `GPLAT_ERRLEVEL_*` 常量从未提交，已直接改名为 `GPLAT_ERRCAT_*`。

| 文件 | 修改 |
|---|---|
| `include/higplat.h` | 新增 `GPLAT_ERRCAT_RESULT`(0) / `GPLAT_ERRCAT_USAGE`(1) / `GPLAT_ERRCAT_CONNECTION`(2)；新增导出函数 `int GetErrorCategory(unsigned int error, const char** message)`；`IsFatalError` 保留以兼容 ABI，改为等价于"类别为 USAGE"；`BUFFER_TOO_SMALL` / `ERROR_BUFFER_TOO_SMALL` 加注释说明区别 |
| `higplat/qbd.h` | `ErrorLevel` → `ErrorCategory { Result, Usage, Connection }`（值取自公开常量），`ErrorInfo::level` → `category`；`GetErrorInfo` 对 `0 < error < MY_ERR_OFFSET`（errno）返回 Connection，描述用 `strerror_r`（线程局部缓冲区，兼容 GNU/XSI 两种签名）；45 个错误码每个都有显式 case，按类别分组；已废弃的 16 个错误码合并为一组，归 Result，描述 "deprecated error code" |
| `higplat/higplat.cpp` | 实现 `GetErrorCategory`；`IsFatalError` 改为调用它 |

### 分类表

| 类别 | 判据 | 错误码 |
|---|---|---|
| Result | 运行结果，调用方按返回码分支 | `TAG_NOT_EXIST`、`ITEM_NOT_EXIST`、`RECORD_NOT_EXIST`、`TABLE_NOT_EXIST`、`DQ_EMPTY`、`DQ_FULL`、`WAIT_TIMEOUT`、`RESPONSE_TIMEOUT`、`REQUEST_QUEUE_FULL`、`ALREADY_LOAD`、`ITEM_ALREADY_EXIST`、`TABLE_ALREADY_EXIST`、`FILE_IN_USE`、`FILE_CREATE_FAILSURE`、`NO_SPACE`、`TABLE_OVERFLOW`、`ITEM_OVERFLOW`、已废弃码、未知码 |
| Usage | 调用方 bug，调用前就能检查出来 | `INVALID_PARAMETER`、`PARAMETER_SIZE`、`RECORDSIZE`、`STRING_TOO_LONG`、`BUFFER_TOO_SMALL`(1038)、`ERROR_BUFFER_TOO_SMALL`(1041)、`FILENAME_TOO_LONG`、`STARTPOSITION`、`OPERATE_PROHIBIT`、`TABLE_ROWID` |
| Connection | 连接不可用 | errno（`< MY_ERR_OFFSET`）、`SOCKET_NOT_CONNECTED`、`INVALID_RESPONSE` |

（表中省略了 `ERROR_` 前缀。）

### 取舍

- `STRING_TOO_LONG`（写入字符串超过 tag 容量）和 `BUFFER_TOO_SMALL`（1038，读出的字符串比缓冲区长）原为 Ignore，按"调用前可检查"归为 Usage，与 `RECORDSIZE`、`ERROR_BUFFER_TOO_SMALL` 一致。若认为字符串超长更像数据问题，可改回 Result（只改 `qbd.h` 一处）。
- 两个"缓冲区太小"的宏名和数值都没动（避免破坏调用方代码），只改描述：1038 为 "string longer than buffer"（服务端 `ReadB_String` 检出，连接保留）；1041 为 "data larger than buffer"（客户端检出，网络 API 会关闭 sockfd）。
- 已核对：本地 API 和服务端都不会产生小于 1000 的错误码，所以"小于 1000 即 errno"的判定成立。

## 二、错误钩子替代库内打印（第 2 项）

### 修改

| 文件 | 修改 |
|---|---|
| `include/higplat.h` | 新增 `typedef void (*GPLAT_ERROR_HOOK)(unsigned int error, int category, const char* message, const char* func, void* user)` 和导出函数 `void SetErrorHook(GPLAT_ERROR_HOOK hook, void* user)` |
| `higplat/higplat.cpp` | 删除 `g_api_depth`；`AutoErrorCheck(error, func)` 析构时若错误码非 0：加锁复制钩子和 user，解锁后调用钩子，调用前后保存/恢复 `errno`；默认钩子 `DefaultErrorHook` 只处理 Usage 和 Connection，`snprintf` 拼好整行后一次 `fputs` 写 stderr |
| `higplat/higplat.cpp` | 拦截器只放在 31 个导出网络函数里：从内部 helper `writeb_`、`writeb_string_`、`writeb_plc`、`writeb_string_plc` 移到导出的 `writeb`、`writeb_notpost`、`writeb_string`、`writeb_string_notpost`（`write_plc_*` 原本就在导出层）；所有调用点改为 `AutoErrorCheck _checker(error, __func__)`。已用脚本核对：31 个导出函数各恰好一个，内部 helper 一个都没有 |

### 行为

- 带 `unsigned int* error` 的网络 API 返回时若错误码非 0（含 `waitpostdata` 超时返回 true + `ERROR_WAIT_TIMEOUT`），调用一次钩子；`func` 为对外的 API 名（如 `writeb`，而不是 `writeb_`）。
- 默认输出（用户确认：默认写 stderr）：`[higplat usage] writeb: record size invalid (code 1014)`、`[higplat connection] readb: Connection reset by peer (code 104)`。Result 类不输出。
- `SetErrorHook(NULL, NULL)` 关闭输出。线程安全；钩子可能在多个线程上并发执行，不得抛异常。没有提供"恢复默认钩子"或"读取当前钩子"的接口（测试里用 fork 隔离）。
- 与改动前相比：输出从 stdout 改到 stderr；`ERROR_TAG_NOT_EXIST` 不再打印；新增打印 Usage 类（如 `INVALID_PARAMETER`）和 Connection 类（以前断线完全不打印）。

## 三、GplatConnection 按类别抛异常（第 3 项）

### 修改（`include/gplat_connection.h`）

用户确认两点：连接类错误抛异常；异常都派生自 `std::runtime_error` 的公共基类。

```cpp
class GplatError : public std::runtime_error {       // what() 为 "<描述> (Code: N)"，格式与改动前相同
public:
    unsigned int code() const noexcept;
};
class GplatUsageError : public GplatError {};        // Usage
class GplatConnectionError : public GplatError {};   // 连接不可用，已标记为关闭
```

`call()` 的顺序：未打开 → 抛 `GplatConnectionError(ERROR_SOCKET_NOT_CONNECTED)`；调用成功 → 返回 error（只有 `waitpostdata` 超时非 0）；失败且 error 为 0 → 按 `ERROR_SOCKET_NOT_CONNECTED` 处理；按 `closed_by_library` 更新连接状态；类别为 Usage → 抛 `GplatUsageError`；连接已关闭 → 抛 `GplatConnectionError`（code 保留原错误码）；否则返回 Result 类错误码。

`closed_by_library` 的 Default 规则改为"类别为 Connection 或 `ERROR_BUFFER_TOO_SMALL`"，与分类表共用一个事实来源，不再单独列错误码。

### 对调用方的行为变化

| 场景 | 改动前 | 改动后 |
|---|---|---|
| `readb` 不存在的 tag | 抛 `std::runtime_error` | 返回 `ERROR_TAG_NOT_EXIST`，连接保留 |
| 队列空、`waitpostdata` / `getresponse` 超时 | 返回错误码 | 不变 |
| `INVALID_PARAMETER`、`PARAMETER_SIZE`、`STRING_TOO_LONG`、`BUFFER_TOO_SMALL`(1038) | 返回错误码 | 抛 `GplatUsageError`，连接保留 |
| `RECORDSIZE` | 抛 `std::runtime_error` | 抛 `GplatUsageError`，连接保留 |
| `ERROR_BUFFER_TOO_SMALL`(1041) | 抛 `std::runtime_error`，连接已关闭 | 抛 `GplatUsageError`，`is_open()` 为 false |
| I/O 失败（errno）、`INVALID_RESPONSE` | 返回错误码，连接标记关闭 | 抛 `GplatConnectionError` |
| 未 `open()` / 连接已关闭后调用 | 返回 `ERROR_SOCKET_NOT_CONNECTED` | 抛 `GplatConnectionError(ERROR_SOCKET_NOT_CONNECTED)` |
| `subscribe` 不存在的 tag | 抛 `std::runtime_error`，连接已被 C 库关闭 | 抛 `GplatConnectionError`，`code()` 为 `ERROR_TAG_NOT_EXIST` |

最后一行是第 4 项的直接后果：`subscribe` / `waitpostdata` 的 C 实现对任何服务端错误都会关闭连接，所以即使错误码属于 Result，封装类也只能按"连接已断开"处理。

现有 `catch (const std::runtime_error&)` 仍能捕获全部异常。方法的返回值现在只会是 0 或 Result 类错误码。

## 六、遗留问题：第 4 项 —— C 库关闭调用方持有的 fd

### 现状与来历

- `higplat.cpp` 的 24 个网络 API 函数中共有 89 处 `close(sockfd)`：I/O 失败、短读、响应校验失败、`ERROR_BUFFER_TOO_SMALL`（响应体未读，流已错位）都会关闭；`subscribe`、`waitpostdata`（以及 `registertag`）对服务端返回的非超时错误也会关闭。
- 这是有意形成的约定。`Doc/commits/260813-02.md`：s7ioserver 写线程在 `waitpostdata` 失败后不自己关闭连接，为不破坏这一约定，补齐了 `subscribe`、`registertag`、`waitpostdata` 所有失败路径的 close。
- 依赖该约定的调用方：
  - `s7ioserver/threadWritePlc.cpp`：`waitpostdata` 失败后直接 `conn = -1` 再重连，不调用 `disconnectgplat`。
  - `toolgplat/monitor.cpp`："waitpostdata 出错时已关闭 conn"、"subscribe 失败时已关闭连接"；用 `shutdown()` 唤醒接收线程，由库在读到 EOF 后关闭 fd（`Doc/commits/260929-02.md`）。
- `GplatConnection` 当初决定"不改 C 库，封装类按错误码判断连接是否已被关闭"（`Doc/commits/260930-02.md`），即 `closed_by_library` + `CloseRule::{Default, AnyServerError}`。

### 问题

1. **调用方无法得知 fd 是否已被关闭。** 同一个返回 false 的调用，有时库已关闭 fd（I/O 错误），有时没有（大多数服务端错误）。调用方：
   - 再调 `disconnectgplat(fd)`：库已关闭时会重复 close；多线程程序中这个 fd 号可能已被别的线程重新分配，会误关别人的连接。
   - 不调：库没关闭时 fd 泄漏，服务端的旧连接（含订阅）也一直保留。现有实例：`s7ioserver/threadReadPlc.cpp` 在 `writeb` 失败后（含 `ERROR_TAG_NOT_EXIST`、`ERROR_RECORDSIZE` 这类不关闭连接的服务端错误）直接 `reconnectGplat()`，旧 fd 泄漏。
2. **封装类只能猜。** `closed_by_library` 的规则要与 89 处 close 分支保持一致，两处分开维护。C 库每增删一条 close 路径都要同步修改。
3. **语义被扭曲。** `subscribe` 一个不存在的 tag 本是 Result（只返回码），但 C 库关闭了连接，`GplatConnection` 只能抛 `GplatConnectionError(ERROR_TAG_NOT_EXIST)`（见第三节表格最后一行）。
4. **`ERROR_BUFFER_TOO_SMALL` 关闭连接只是因为响应体没读完。** 把剩余包体读掉（drain）即可保留连接，这样它就是一个纯粹的 Usage 错误。

### 相关遗留缺陷（已实测确认，修第 4 项时应一并处理）

1. **对端关闭（EOF）被当成成功。** `readn()` 读到 EOF 时返回已读字节数（可能为 0）而不是 -1。24 个调用 `readn` 的函数中，只有 `subscribe`、`waitpostdata`、`getresponse`、`registertag` 比较了返回长度，其余 20 个只判断 `< 0`。由于 `msg` 里还是刚发出的请求头（`error = 0`、`bodysize = 0`），后续检查全部通过。实测：用一个 accept 后立即关闭的假服务端，`readb` 返回 `ok=1, err=0`，输出缓冲区原样未动。
2. **SIGPIPE 会杀死客户端进程。** `send_all()` 调用 `send(..., 0)`，没有 `MSG_NOSIGNAL`；s7ioserver、toolgplat、testapp、testsuite 也都没有忽略 SIGPIPE。实测：上一条之后再调一次 `readb`，进程被 SIGPIPE 终止（退出码 -13）。
3. 次要：`connectgplat` 失败时用 `fprintf(stderr, ...)` 直接打印，不经过错误钩子（它没有 `error` 参数）。

### 方案选项

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 不改约定，补可靠信号 | C 库用 thread_local 记录"本次调用是否关闭了 fd"，导出如 `bool LastCallClosedFd(void)`；`GplatConnection` 用它取代 `closed_by_library` | 不改 ABI 和现有调用方行为；封装类不再猜 | C 调用方仍要多调一个函数才能知道；`subscribe` 的语义扭曲仍在 |
| B. 改约定：库不再关闭调用方的 fd | 失败一律只返回错误码，fd 始终归调用方，由调用方 `disconnectgplat`；连接已不可用由 Connection 类错误码表达（读到 EOF 或协议错位时，库只能 `shutdown()`，不能 `close()`，让 fd 号保持有效直到调用方关闭） | 所有权清晰，没有重复关闭 / 泄漏的歧义；`closed_by_library` 可删除，改为"Connection 类即断开" | 行为变更：s7ioserver 写线程、toolgplat monitor 必须同步改为自己关闭，外部 C 调用方若依赖旧约定会泄漏 fd；89 处 close 要逐一改 |
| C. 局部修正（可与 A 或 B 组合） | `readn` EOF 视为连接错误；`send` 加 `MSG_NOSIGNAL`；`ERROR_BUFFER_TOO_SMALL` 时 drain 包体并保留连接；`subscribe` / `waitpostdata` 对服务端错误不再关闭连接 | 前两条是纯缺陷修复，不改约定；后两条消除第 3、4 点 | 后两条本身就是改约定，需同步 `closed_by_library` 与 toolgplat / s7ioserver |

建议顺序：

1. 先修两个已确认的缺陷：`readn` EOF 视为连接错误、`send` 加 `MSG_NOSIGNAL`。不改约定，风险低，补测试即可。
2. 再在 A 和 B 之间做决定。仓库内依赖旧约定的调用方只有 s7ioserver 写线程和 toolgplat monitor，B 的改动面可控，长期更干净；若要保证外部 C 调用方行为不变，选 A。

### 实施时的影响面

- `higplat/higplat.cpp`：89 处 `close(sockfd)`（24 个函数）、`readn` / `send_all`。
