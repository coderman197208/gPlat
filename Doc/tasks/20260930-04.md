## 结论

是设计问题，但瓶颈不在线程池。真正卡住吞吐的是**唯一的发送线程**，其次是**唯一的 epoll 接收线程**，再加上每个请求都要在线程之间交接两次。线程池里的实际业务只是往 mmap 里做一次 memcpy，每条消息只需几微秒。所以加工作线程并不会加快处理，反而带来更多线程唤醒和锁竞争，结果变慢。

## 复现与测量

我在 `gp2` 起了一个独立实例（端口 18777），配置和二进制与仓库相同，仓库代码没有改动。用 `/proc/<pid>/task/*` 统计 gplat worker 进程里每个线程的 CPU 时间和主动上下文切换次数。第 2 阶段共 10×50×100×3 = 150,000 个请求。

| 工作线程数 | 2阶段耗时(ms) | epoll线程 CPU / 切换次数 | 工作线程合计 CPU / 切换次数 | **发送线程** CPU / 切换次数 |
|---|---|---|---|---|
| 1 | 3490 | 780ms / 81k | 1170ms / 70k | **2340ms** / 70k |
| 2 | 5206 | 1080ms / 139k | 3120ms / 277k | **3030ms** / 138k |
| 5 | 5297 | 1170ms / 137k | 3350ms / 284k | **3000ms** / 136k |

耗时与你的结果一致。数据说明了四点：

1. **最忙的是发送线程，不是工作线程。** N=1 时它在 3.49s 里用了 2340ms CPU，约 67% 满载，每条消息约 15µs。原因是所有连接的 `send()` 都由这一个线程串行执行。在回环网卡上，`send()` 会同步走完对端的 TCP 接收路径，还要唤醒客户端线程；在 WSL2 上，跨 vCPU 唤醒的代价很高。相比之下，工作线程每条消息只要约 7.8µs，而且当前构建没有开优化（`-O0`）。
2. **N=1 时有天然的批处理，N≥2 时没有了。**
   - N=1：唯一的工作线程经常处于忙碌状态，消息会在队列里积压，工作线程和发送线程每醒一次能处理约 2 条消息。
   - N≥2：总有空闲的工作线程，每条消息都要单独唤醒一个线程。各阶段的上下文切换次数翻倍，工作线程总 CPU 从 1170ms 涨到 3350ms，干的是同样的活。
3. **线程越多，下面这些锁的竞争越激烈：**
   - **发送线程在整个遍历期间持有 `m_sendMessageQueueMutex`，每一次 `send()` 系统调用都在锁内**（见 `ngx_c_socket.cxx:768` 到 `ngx_c_socket.cxx:914`）。工作线程调用 `msgSend()` 时会被挡住，发送线程释放锁后还要逐个唤醒它们。
   - 线程池的 `m_pthreadMutex` 由 epoll 线程和所有工作线程共用。
   - Board 读写：每次 `WriteB` 都要依次拿全局 `mutex_rw`（在 `higplat.cpp:238` 的 `fetchtab` 里）、整块 Board 的 `pmutex_rw`、再加分段锁。而 testapp2 有 2/3 的写操作落在 `TagBigData1` 和 `string1` 这两个 tag 上，总是争同一把分段锁。
4. **这个测试本身就无法体现并发优势。** 10 个同步连接意味着同时在途的请求最多 10 个。按 Little 定律，单次请求延迟 = 10 / 吞吐：N=1 时约 233µs，N=5 时约 353µs。多出来的工作线程没有可以并行的活。

## 原型验证

原型只改在 `repo` 的副本里，仓库没动。改动两处：
- `msgSend()` 在工作线程里直接做非阻塞 `send()`。用一把每连接的锁保护，只有当这个连接既没有积压消息、也没有在等 EPOLLOUT 时才直接发。
- 发送线程只处理积压消息：先在锁内把整个队列交换出来，再在锁外发送。

| 工作线程数 | 原版(ms) | 原型(ms) |
|---|---|---|
| 1 | 3490 | ~1860 |
| **2** | 5206 | **~1030** |
| 3 | — | ~1510 |
| 5 | 5297 | ~1760 |
| 10 | — | ~1750 |
| 不用线程池（epoll 线程内直接处理并直接发送） | — | ~2090 |

去掉发送线程这个瓶颈后，N=2 比原版最好的成绩快约 3.4 倍，多线程开始有收益。

但 N≥3 又会变慢：N=5 时 epoll 线程在 1765ms 内用了 1810ms CPU，已经跑满。它的开销主要在每收到一条消息就 `pthread_cond_signal` 唤醒一个在休眠的工作线程（在 `ngx_c_threadpool.cxx:196`），这是第二个瓶颈。

## 设计缺陷清单（按影响排序）

1. **单一发送线程串行完成所有 `send()`，而且发送期间一直持有全局队列锁。** 这是主要原因。
2. **每个请求要经过两次跨线程交接**（epoll 线程 → 线程池 → 发送线程）。这套框架来自 nginx 教学项目，适合业务逻辑较重的场景；gPlat 的操作只有几微秒，交接的代价比处理本身还大。
3. **只有一个 epoll 线程负责接收。** 每个包分两次 `recv()`（先收包头、再收包体），并且每条消息都在 `ngx_c_socket_request.cxx:255` 调用一次唤醒。
4. **Board 每次读写都要拿两把全局锁**（`mutex_rw` 和 `pmutex_rw`）。另外 `mutex_rw_tag[64]` 是连续排列的 `std::mutex`（每个 40 字节），会有伪共享。
5. **发送线程有一个潜在的消息乱序问题。** 遇到 `iThrowsendCount > 0` 时它会跳过这条消息；如果遍历过程中计数降回 0，同一连接后面的消息就可能先于前面的发出去。只在发送缓冲区满时才会出现。
6. **Makefile 只有 `-g`，没有 `-O2`。** 不是设计问题，但所有耗时数据都被放大了。

**testapp2 自身也有一个 bug。** `threadfunction.cpp:168` 在收到 `WAIT_TIMEOUT`、但 `exitloop` 还是 false 时，仍然会执行到 `threadfunction.cpp:175`。它会去读一个不存在的 tag `WAIT_TIME01`，然后触发 assert。服务端变快以后，这种情况就会出现（原型 N=2 时多次复现）。收到超时后应该直接 `continue`。

## 建议

- **短期（改动小、收益最大）：** 按上面原型的方式，让工作线程直接发送，发送线程只负责积压和 EPOLLOUT 的情况；同时不要在持有全局锁时调用 `send()`。改完后工作线程数建议设为 2 到 4。
- **中期：**
  - epoll 线程把一次 `epoll_wait` 收到的所有消息批量入队，只唤醒一次。
  - 用更大的缓冲区 `recv`，一次解析多个包。
  - Board 的索引查找改用 `shared_mutex`，分段锁按 64 字节对齐。
- **长期：** 改成"每个线程一个事件循环"（多 Reactor）。N 个 I/O 线程各自管理一部分连接，在同一个线程里完成接收、处理、发送，没有任何交接；线程池只留给慢操作。memcached、muduo 都是这样扩展的。
- **测试方法：** 用 `-O2` 构建。要测多线程扩展性，就增加连接数或并发请求数，并且不要让所有线程都写同样的两个 tag。

## 不加同步会出现的三种冲突

1. **字节交错。** 服务端 socket 是非阻塞的。内核能保证一次 `send()` 写入的字节是连续的，但如果发生部分发送，剩下的字节还留在用户态。此时另一个线程把它的消息整条写进去，前一条消息的剩余部分只能排在后面，TCP 字节流就乱了，客户端会按错误的包头解析。10KB 的字符串消息、客户端读得慢的时候，部分发送很常见。
2. **消息顺序错乱。** 发给同一连接的两条消息，谁先调用 `send()` 谁就先到。
3. **"未发完"状态被覆盖。** 每个连接只有一组未发完状态：`psendMemPointer`、`psendbuf`、`isendlen`、`iThrowsendCount`。两个线程同时遇到部分发送，会互相覆盖这些字段，导致内存泄漏、重复释放或数据丢失。

## gPlat 里同一连接真的会有多个发送方

客户端虽然是同步的，每个 socket 同时只有一个请求，但服务端可能从多个线程给同一个连接发消息：

- 处理该连接自身请求的工作线程，发回应答。
- 其他连接的工作线程，通过 `NotifySubscriber` 发 POST 事件；`getresponse` 的 `DeliverResponse` 也是这种情况。
- 定时器线程：`WAIT_TIMEOUT`、POST_DELAY、请求超时、`NotifyTimerSubscriber`。

这些调用大多在 `logicPorcMutex` 锁内，并靠标志位保证只发一条，但不是全部。例如 `HandleClearQ`、`HandleClearB` 和 POST_DELAY 的回调都没有拿这把锁。所以不能依赖 `logicPorcMutex`，传输层必须自己保证串行。

## 原型怎么避免冲突

- **每连接一把 `sendMutex`。** 同一个 fd 在任何时刻只有一个线程在调用 `send()`，不管它是工作线程、定时器线程还是发送线程。
- **只有在"前面没有未完成的消息"时才直接发。** 在 `sendMutex` 内检查 `iSendQueued == 0 && iThrowsendCount == 0`，否则就排队，这样能保持先进先出。
- **部分发送时交给 EPOLLOUT 继续发。** 在剩余部分发完、积压消息清空之前，这个连接的后续消息一律排队。
- **发送线程处理积压时也拿同一把 `sendMutex`。** 同一轮里用 `blocked` 集合保证顺序，发不出去的消息放回队列头部。
- **锁顺序固定为 `logicPorcMutex` → `sendMutex` → `m_sendMessageQueueMutex`。** 发送线程在持有全局队列锁时从不去拿 `sendMutex`，所以不会死锁。
- **持锁时间很短。** socket 是非阻塞的，`send()` 不会阻塞。不同连接的锁互不相干，完全可以并行发送，这正是性能提升的来源。只有同一连接同时有多条消息要发时才会争这把锁，这种情况很少。

## 正式实现前还要修的 3 个问题

这三个问题原版就有，改成直接发送后更需要处理。

1. **消息可能卡住不发。** `ngx_c_socket_request.cxx:355` 先 `sem_post`，到 `ngx_c_socket_request.cxx:360` 才 `--iThrowsendCount`。发送线程可能被唤醒时计数还大于 0，于是把消息放回队列；之后没有新的唤醒，消息就一直卡着，直到别的连接有流量。修法：先减计数再 `sem_post`，或者由 epoll 线程在写完后直接清掉这个连接的积压。
2. **关闭连接和发送之间有竞态。** `ngx_c_socket_request.cxx:130` 先 `close(fd)`，之后 `inRecyConnectQueue` 才递增 `iCurrsequence`。一个已经通过序号检查的发送方，可能对已关闭的 fd 调用 `send()`；如果 fd 编号已被复用，数据就会发给别的客户端。修法：在 `sendMutex` 内完成关闭和序号递增。
3. **POST_DELAY 回调不加锁。** `ngx_c_slogic.cxx:675` 的回调在没有 `logicPorcMutex` 的情况下读写 `m_bWaitingPost` 和 `m_listPost`。它可能和 `NotifySubscriber` 或超时同时发出消息，结果一次 `waitpostdata` 收到两条，客户端的协议就错位了。这是协议层的问题，`sendMutex` 解决不了。回调里需要拿 `logicPorcMutex`，并先检查 `iCurrsequence`，确认连接没有被回收。

## 服务端改动（`gplat`）

- **每连接一把发送锁。** 连接结构里新增 `sendMutex` 和 `iSendQueued`（该连接在发送队列里还没发出的消息数）。发送状态的读写，以及对这个 fd 的 `send()`/`close()`，都在这把锁内进行。
- **`msgSend()` 改为直接发送。** 只要连接上既没有排队消息、也没有等 EPOLLOUT 的剩余数据，就在调用它的线程里直接 `send()`；否则排队交给发送线程，这样顺序不变。发送逻辑抽成了 `sendMsgLocked()`。
- **发送线程只处理积压消息。** 它先在锁内把整个队列取走，再在锁外发送。同一连接如果还在等 EPOLLOUT，它这一轮后面的消息也一起推迟，然后放回队列头部。
- **修复"消息卡住不发"。** `ngx_write_request_handler` 现在在锁内先把 `iThrowsendCount` 减掉，然后才去唤醒发送线程。
- **修复"关闭与发送的竞态"。** 新增 `ngx_close_and_recycle()`：在锁内关闭 fd、递增序号，并丢掉这个连接还没发完的数据。发送方也在同一把锁内检查序号，因此不会再往已关闭或已被复用的 fd 上发数据。
- **修复 POST_DELAY 回调不加锁。** 回调里改为先拿 `logicPorcMutex`，再检查序号。
- 锁的获取顺序固定为 `logicPorcMutex` → `sendMutex` → `m_sendMessageQueueMutex`，已写进 `CLAUDE.md`，`ARCHITECTURE.md` 也同步更新了。

## 发现但没处理的问题

- 连接断开后，`m_listPost` 里剩下的 POST 不会被清理。这个连接对象被新客户端复用后，新客户端的 `waitpostdata` 可能取到旧消息，然后收不到任何回应。
- `recvproc` 遇到 EAGAIN 或 EINTR 时返回 -1，会被当成断开处理：取消订阅，但连接并没有关闭。
- 3 个及以上工作线程时仍比 2 个慢。原因是 epoll 线程每收到一条消息就要唤醒一个在休眠的工作线程，这要靠后续批量派发来解决。
