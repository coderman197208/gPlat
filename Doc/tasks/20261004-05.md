# 20261004-05 B1 修复：DeleteItem 与读写竞态

本轮修复测试套件登记的缺陷 B1（`DeleteItem` 的 memmove 不持条带锁，与 `readb` 竞态 → 撕裂读），并把对应用例从 XFAIL 转为普通回归用例。

## 一、问题

Board 有两层锁：全局板锁 `pmutex_rw`（保护哈希索引）和 64 把条带锁 `mutex_rw_tag[]`（按 tag 位置 `loc & 63` 保护数据访问）。

1. `DeleteItem` 只持全局锁就对整个数据区（约 8MB）和类型区做 memmove，搬移其它 tag 的数据，与持条带锁的 `ReadB`/`WriteB` 不互斥 → 读到搬移中途的数据（撕裂读）。
2. 读写函数先释放全局锁、再获取条带锁。两锁之间 tag 可能被 `DeleteItem` 删除或搬移，随后用过期的 `loc` 访问数据。
3. `ClearB` 重置整个索引，同样只持全局锁，存在相同竞态。

## 二、修改（`higplat/higplat.cpp`）

| 函数 | 修改 |
|---|---|
| 新增 `StripeLockAll` | RAII：按 0..63 升序锁住全部条带锁，析构时逆序释放。调用者须已持全局锁 |
| `DeleteItem` | 持全局锁后再持 `StripeLockAll`，然后才做 memmove 与索引修正 |
| `ClearB` | 同上，重置索引期间排除所有读写者 |
| `ReadB`、`ReadB_String`、`ReadB_String2`、`WriteB`、`WriteB_String` | 先获取条带锁，再释放全局锁（原为先放全局锁再拿条带锁），消除两锁之间的窗口。`WriteB`/`WriteB_String` 同时去掉了多余的 `else` 分支 |

### 锁序

统一为：全局板锁 → 条带锁（升序）。

- 条带锁只在持有全局锁时获取（共 7 处：上述 5 个读写函数 + `DeleteItem` + `ClearB`），不存在持条带锁再拿全局锁的路径。
- 读写者最多同时持一把条带锁，且持锁期间只做 memcpy/memset，总能释放。
- 批量加锁者（`DeleteItem`/`ClearB`）加锁前已持全局锁，同一时刻至多一个线程在批量加锁；升序是为将来新增批量加锁点预留的防御性约定。
- 进程级 table 锁（`fetchtab` 等）在返回前释放，与板锁没有嵌套。

## 五、遗留（与本次无关）

板内 `std::mutex` 放在 mmap 共享内存中，不是 robust mutex；进程在持锁时崩溃会使其他进程阻塞。
