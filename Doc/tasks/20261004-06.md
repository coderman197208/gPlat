# 20261004-06 G1 修复：deletetag 清理 response_tag 归属表

本轮处理测试套件登记的缺陷 G1（`m_mapResponseOwner` 永不 erase），并把对应用例从 XFAIL 转为普通回归用例。

## 一、问题与结论

`HandleGetResponse` 每次请求都写 `m_mapResponseOwner[response_tag] = request_tag`，全文件没有 `erase`。

按设计文档（`Doc/commits/260926-05.md`），“一个 response_tag 只对应一个 request_tag，服务端在进程期内记住归属”，且强制检查（违反返回 `ERROR_INVALID_PARAMETER`）。因此：

| 现象 | 结论 |
|---|---|
| 请求解决后 response_tag 不能被别的 request_tag 复用 | **设计行为**，不是缺陷 |
| 条目无界累积 | 不成问题：response_tag 必须事先在 Board 创建，条目数受 tag 数量限制 |
| tag 被 `deletetag` 后条目残留：旧绑定仍在；同名 tag 重建为普通 tag 后，写入会被当作 response_tag（只写 Board、不通知普通订阅者，并记“丢弃无人等待的响应”） | **真实问题**，本轮修复 |

## 二、修改

### 服务端（`gplat/ngx_c_slogic.h` / `.cxx`）

- 新增 `CLogicSocket::ForgetDeletedTag(const char* tagName)`，持 `m_reqMutex` 遍历 `m_mapResponseOwner`：
  - 被删 tag 作为 **response_tag** 的条目：直接删除；
  - 被删 tag 作为 **request_tag** 名下的条目：仅当该 request_tag 在 `m_mapReqChannel` 中没有挂起/排队请求时删除，否则保留，避免已发出请求收不到响应。
- `HandleDeleteItem` 在 `DeleteItem` 成功后、取 `logicPorcMutex` 之前调用。只持 `m_reqMutex`，不违反锁序（`logicPorcMutex` → `sendMutex` → `m_sendMessageQueueMutex`，持 `m_reqMutex` 时不取 `logicPorcMutex`）。

限制：经本地 mmap API 直接删除 tag（不经服务端）不会触发清理。
